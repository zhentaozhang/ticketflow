# 项目口述介绍

> 用于面试自我介绍或 HR 问"介绍一下你的项目"时，口头讲述用。
> 共三档：30 秒精简版（HR/开头用）、1 分钟完整版（面试官用）、以及每个技术点的展开话术。

---

## 一、30 秒精简版（HR / 开场）

面试官您好，我介绍一个我主要负责的后端项目——一个高并发在线票务交易系统，主要服务演唱会、体育赛事这类抢票场景。

这类场景的核心挑战是开票瞬间流量暴增，所以整个项目都围绕高并发来设计。我做的工作主要有四块：一是用 ShardingSphere 做订单分库分表，让订单号能直接定位到对应分片；二是封装了一套分布式锁框架；三是做了 Caffeine 加 Redis 加 MySQL 的多级缓存；四是把下单链路改造成 Redis 加 Kafka 的异步架构。下面我展开讲一下这几块。

---

## 二、1 分钟完整版（面试官 / 项目详述）

**背景。** 这个系统是面向演唱会、体育赛事的高并发在线票务平台，核心难点是开票瞬间会产生极高的流量峰值，我要解决的是三件事：库存不能超卖、高峰流量能扛住、系统要稳定可用。

**第一块，订单分库分表。** 我基于 ShardingSphere 自定义分片算法，用基因法把用户 ID 的哈希信息编码进订单号里。这样不管业务方拿用户 ID 查还是拿订单号查，都能精准路由到同一个分片，避免了跨库查询和读扩散。

**第二块，统一分布式锁框架。** 我封装了一套分布式锁，支持可重入锁、公平锁、读写锁多种模型，业务上用注解就能声明。关键点是我调整了 AOP 和事务拦截器的执行顺序，保证加锁先于事务开启、释放晚于事务提交，从框架层面解决了锁和事务的时序竞态问题。

**第三块，多级缓存。** 我搭建了 Caffeine 加 Redis 加 MySQL 三级缓存。用 Redis Stream 广播缓存失效事件，让集群里每个实例的本地缓存同步失效；同时利用 Caffeine 的同 Key 请求合并，避免缓存击穿时数据库压力被放大。

**第四块，异步下单链路。** 我把下单流程改造成 Redis 加 Kafka 的异步架构：用 Lua 脚本保证库存扣减的原子性，防止超卖；用 Kafka 做流量削峰，把订单落库解耦成异步；再用延迟任务实现超时订单自动取消和库存回补。

大概就是这四块，每一块我都能再展开讲讲里面遇到的问题和取舍。

## 三、展开话术（被追问时逐块深入）

> 每块先说"做了什么"，再说"为什么这么设计"，最后说"有什么代价/坑"。

### 1. 订单分库分表：基因法路由

我们订单表做了分库分表，但分库分表最头疼的问题是：用户拿 user_id 查"我的订单"，支付回调又只能拿 order_number 查详情，这两个查询入口如果路由不到同一个分片，就得广播查询再合并结果，成本很高。

所以我在生成订单号的时候，把 user_id 的部分位编码进去，让订单号和 user_id 共享同一个路由基因。这样不管用哪个字段，都能通过位运算直接定位到同一个分片，不需要额外维护映射表，也避免了读扩散。

这个方案也有代价，就是订单号必须由我们统一生成，不能让外部随便传；而且基因位的宽度决定了未来最多能扩到多少分片。这些我在设计的时候都有考虑。

### 2. 分布式锁框架：锁与事务时序

项目里很多场景需要分布式锁，但直接用 Redisson 散落在业务代码里会很乱，也容易忘释放。所以我做了一套统一封装：支持可重入锁、公平锁、读写锁几种模型，业务上用注解声明锁名称、锁 key、锁类型和等待时间就行，AOP 切面统一处理加锁、释放和异常。

这里面比较难的点是锁和事务的时序问题。如果锁在事务提交之前就释放了，其他请求进来读到的还是旧数据，锁就白加了。我通过调整 AOP 和事务拦截器的执行顺序，保证进入方法时先加锁再开事务，退出时先提交事务再释放锁，从框架层把这个时序问题解决掉。

### 3. 多级缓存：Caffeine + Redis + MySQL

我们做了三级缓存，Caffeine 在 JVM 内、Redis 跨实例共享、MySQL 是最终数据源。加 Caffeine 是为了降低访问成本，热点数据直接在本地命中，不用每次都走网络。

但本地缓存有个问题：每个实例各存一份，数据会不一致。我的做法是用 Redis Stream 广播缓存失效事件，数据变更时往 Stream 发一条消息，所有实例收到后删掉自己的本地缓存，下次请求重新加载，只保证最终一致。选 Stream 而不是 Pub/Sub，是因为消息要持久化、要可靠，Pub/Sub 丢了就丢了。

另外击穿场景我也做了防护：Caffeine 的同 Key 请求合并，让同时 miss 的请求只有一个真正去回源，避免热点 Key 失效瞬间数据库被放大 N 倍。

### 4. 异步下单：Lua + Redis + Kafka

下单链路如果全同步，用户要等数据库落库，高并发下线程会被慢 IO 占满。我改成同步受理、异步落库：请求进来先做校验，然后跑一段 Lua 脚本，在 Redis 里原子完成余票校验、锁座、扣库存，成功后就发消息到 Kafka，马上把订单号返回给用户。

Lua 脚本的意义在于它作为一条命令交给 Redis 单线程执行，里面的多步操作对外是原子的，从根上杜绝了超卖。Kafka 的作用是削峰和解耦，数据库按自己的消费能力慢慢落库，而不是直接承受入口流量。超时的订单用延迟任务自动取消并回补库存。

## 四、HR 版补充（讲完项目后可以主动带一句）

整体下来，我觉得这个项目最大的收获是让我理解了互联网交易系统在高并发下是怎么一层层做取舍的：为了保证库存一致性，我选择了 Redis 加 Lua 的原子方案；为了吞吐，我把慢操作异步化；为了稳定，我用多级缓存和失效广播去兜底。这里面每一个设计都不是堆技术，而是针对真实场景权衡出来的，我对整个链路都比较熟，可以随时展开。
