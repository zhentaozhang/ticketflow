# 统一分布式锁框架

## 动机与选型

**Q：你们哪些业务真的需要分布式锁？不加锁会发生什么？**

A：我们主要在三类场景使用分布式锁。第一类是订单状态流转，例如支付回调和超时取消可能并发修改同一个订单，如果不加锁可能出现已支付订单被取消、重复退款等状态异常，因此按订单号加锁保证状态变更串行。第二类是下单资源控制，例如锁座位、扣减库存，如果多个请求同时操作同一资源，会导致超卖问题，这里按照节目和票档维度控制锁粒度。第三类是缓存和消费幂等场景，例如缓存失效时避免大量请求同时回源，以及 Kafka 消费时避免重复处理。所以分布式锁主要解决的是共享资源并发修改导致的数据一致性问题。

------

**Q：本地锁为什么解决不了？分布式锁的本质要求是什么？**

A：本地锁只能保证单个 JVM 内部线程互斥，而实际服务通常是多实例部署，同一个订单或资源的请求可能被不同实例处理，本地锁无法跨进程生效。分布式锁的本质是提供一个跨进程的互斥机制，让多个服务实例竞争同一个锁资源，保证同一时间只有一个实例执行关键逻辑。同时还需要解决锁自动释放、异常宕机、续期以及可重入等工程问题。

------

**Q：Redis、ZK、DB 三种实现怎么选？为什么选择 Redis？**

A：这三种方案我们都评估过。Redis 分布式锁基于内存操作，性能和吞吐较高，并且项目本身已经大量使用 Redis，基础设施复用成本低，同时 Redisson 提供了自动续期、可重入等完善能力。Zookeeper 一致性更强，临时节点机制可以感知客户端异常，但写路径需要经过 ZAB 协议，性能和部署成本更高，不适合作为高频业务锁。数据库锁依赖数据库行锁实现，会占用连接资源，性能较差，也缺少自动续期能力。因此在当前高并发交易场景下，我们选择 Redis + Redisson 作为分布式锁方案。

------

**Q：为什么不自己基于 SETNX 实现？自己实现会有哪些问题？**

A：SETNX 只能完成最基础的抢锁操作，完整实现分布式锁还需要处理很多边界问题。首先是死锁问题，需要设置过期时间，避免服务宕机后锁无法释放；其次是误删问题，锁释放时不能直接删除，需要校验锁持有者身份，并通过 Lua 保证判断和删除的原子性；另外还需要支持可重入，否则同一线程重复加锁会造成死锁；同时还要考虑主从切换导致锁丢失的问题。Redisson 已经封装了这些能力，包括看门狗续期、可重入机制以及安全释放锁，因此我们选择基于 Redisson 做业务层封装，而不是重复实现底层锁逻辑。

## Redisson 原理

**Q：看门狗自动续期原理?为什么需要它?默认 30 秒是怎么定的?**

A：看门狗解决的是分布式锁过期时间不好设置的问题。锁必须设置过期时间，避免服务宕机后永久占用，但时间太短可能业务还没执行完锁就释放，时间太长又会影响故障恢复。Redisson 默认不开启固定 leaseTime 时，会给锁设置 30 秒租约，同时启动后台续期任务，每隔约 10 秒检查锁是否仍被当前线程持有，如果还持有就把过期时间重新刷新为 30 秒。业务正常释放锁或者线程结束后，续期任务停止。这样锁的生命周期和业务执行时间绑定，不需要提前估算执行耗时。

------

**Q：业务执行时间超过锁时间怎么办?为什么还要提供显式 leaseTime?**

A：默认情况下由看门狗自动续期，只要持有锁的线程正常运行，业务执行多久都不会因为锁过期导致并发进入。但看门狗依赖续期线程正常工作，如果实例长时间阻塞或者发生异常停顿，续期可能失败。因此框架也提供显式 leaseTime，用于一些执行时间可控、希望限制最大持有时间的场景。两者区别是，看门狗更关注业务完整执行，leaseTime 更关注故障后的快速释放，避免锁长期占用。

------

**Q：leaseTime 太短业务没执行完、太长故障恢复慢,你们怎么设置?**

A：主要根据业务耗时和故障恢复要求权衡。下限需要覆盖业务正常执行时间，包括数据库操作、远程调用、重试等情况，否则锁提前释放会导致并发问题；上限则取决于业务能够接受的最大等待时间。一般会根据实际 RT 和超时时间预留一定缓冲，不会设置得刚好等于业务耗时。实际开发中大部分场景使用看门狗，只有执行时间明确、需要严格控制锁生命周期的场景才使用固定 leaseTime。

------

**Q：可重入锁为什么重要?你们哪些场景会用到?**

A：可重入锁指同一个线程可以重复获取同一把锁，内部通过计数记录获取次数，释放时递减，直到计数归零才真正释放。它主要解决嵌套调用导致的自死锁问题，比如外层方法已经持有订单锁，内部调用另一个同样需要订单锁的方法，如果锁不可重入，第二次获取会一直等待自己释放。我们默认使用可重入锁，因为业务代码经过封装后，经常存在方法之间相互调用的情况，可重入可以避免这类隐藏死锁。

------

**Q：公平锁原理?什么场景会选择公平锁?**

A：公平锁的核心是按照请求顺序排队获取锁，避免部分请求长期抢不到锁。Redisson 通过 Redis 队列维护等待顺序，释放锁时唤醒队列中的下一个请求。但公平锁需要额外维护队列，增加 Redis 操作次数，因此性能低于默认的非公平锁。我们的框架提供公平锁能力，但实际业务很少使用，因为订单、库存这类场景更关注吞吐和快速失败，不要求严格先来后到。

------

**Q：读写锁原理?什么场景适合使用?为什么实际用得少?**

A：读写锁把访问分成读锁和写锁，多个读请求可以同时执行，但写请求需要独占，适合读多写少的共享数据场景。例如缓存加载、配置读取等场景，多个请求可以并发读取，更新时再加写锁保证一致性。实际使用较少，因为大部分高并发读场景已经通过多级缓存、本地缓存和请求合并解决；真正需要强一致写控制的场景，比如库存扣减，更多依赖 Redis Lua 原子操作，而不是通过锁串行化请求。

------

**Q：四种锁模型怎么设计的?为什么可以一行切换锁类型?**

A：我们对 Redisson 锁进行了统一封装。首先定义统一锁接口，抽象加锁、释放、超时等操作；然后分别实现可重入锁、公平锁、读写锁等不同策略；最后通过工厂根据锁类型返回对应实现。业务侧通过注解配置 lockType，AOP 切面解析注解后选择对应锁实现，业务代码不感知具体锁类型。这样切换锁模型只需要修改一个枚举配置，新增锁类型也只需要扩展实现，不影响已有业务。

## 注解式与锁事务时序

**Q：为什么做成注解式?业务方怎么声明?编程式工具又在什么时候用?**

A：注解式主要是为了把锁逻辑从业务代码中抽离。业务方只需要声明锁名称、锁粒度 key、锁类型和等待时间，AOP 切面统一完成加锁、释放、异常处理，避免重复写 try/finally，也减少忘释放锁的问题。比如订单场景直接在方法上配置订单号作为 key 即可。编程式主要用于动态场景，比如锁粒度需要运行时决定，或者必须先解析请求内容才能确定锁 key，这类场景注解无法提前描述，就通过工具类手动加锁，并在 finally 中释放。

------

**Q：注解式锁的实现原理?锁 key 怎么根据方法参数动态生成?**

A：核心是通过 AOP 拦截带锁注解的方法。切面获取注解中的业务名称和 key 表达式，通过 SpEL 解析方法参数，动态计算出实际锁 key，再拼接成完整锁名称。之后根据注解中的锁类型从工厂获取对应实现，加锁成功后执行目标方法，最终在 finally 中释放锁。锁名称通常由业务前缀、业务标识和具体资源 key 组成，保证不同业务之间不会冲突，同时同一资源能够竞争同一把锁。

------

**Q：锁和事务的时序问题:如果锁在事务提交前释放,会有什么问题?**

A：会导致锁保护范围失效。锁释放代表其他请求可以进入，但如果事务还没有提交，其他请求看到的仍然是旧数据。比如支付回调修改订单状态为已支付，锁提前释放后，取消订单请求获取锁，查询到的还是未支付状态，就可能继续执行取消逻辑，最终产生状态冲突。所以锁的生命周期必须覆盖事务提交，确保其他线程进入时，前一个事务的数据已经对外可见。

------

**Q："加锁先于事务开启、释放晚于事务提交"怎么保证?Spring 里如何控制?**

A：主要通过 AOP 顺序控制。我们将锁切面的优先级设置高于事务切面，让进入方法时先执行锁逻辑，再开启事务；方法执行结束时，事务先提交，锁切面最后执行 finally 释放锁。这样锁覆盖完整事务周期。这个方案依赖锁和事务作用在同一个代理方法上，如果事务在外层方法，或者发生自调用导致代理失效，顺序就无法保证，所以这类情况需要额外约束。

------

**Q：幂等切面、锁切面、事务拦截器同时存在时,执行顺序怎么设计?**

A：顺序设计为幂等切面、锁切面、事务拦截器。幂等放最外层，先判断请求是否已经处理过，避免重复请求继续进入后面的锁和事务；锁放中间，解决多个请求同时操作同一资源的问题；事务放最内层，保证单次业务执行的数据一致性。这个顺序对应三个不同职责：先判断是否执行，再控制并发，最后保证执行结果正确。

------

**Q：防重复提交和分布式锁分别解决什么问题?为什么不能只保留一个?**

A：两者解决的问题不同。防重复提交解决的是同一个请求重复执行，例如用户重复点击、消息重复投递、支付回调重试，通过幂等标识保证同一请求只生效一次。分布式锁解决的是不同请求之间的并发冲突，例如支付和取消同时修改订单、多个请求同时扣减资源。只使用其中一个都不够，幂等不能解决不同请求之间的并发问题，锁也只能保证持锁期间互斥，无法阻止之后相同请求再次执行。

------

**Q：幂等标记什么时候写入?为什么必须在事务提交之后?**

A：幂等标记需要在业务成功提交之后写入。如果事务还没提交就写标记，可能出现业务回滚但幂等记录已经存在的问题，后续相同请求会被误判为成功，导致数据没有落库但无法重试。因此我们通过 Spring 事务同步机制，在事务提交成功后的回调阶段写入幂等标记；如果当前没有事务，则业务成功后直接写入。这样可以保证幂等状态和业务结果保持一致。

## 使用与可靠性

**Q：锁粒度怎么设计?锁用户维度和锁节目维度分别用在什么场景?**

A：锁粒度本质是互斥范围和并发能力之间的权衡，粒度越粗安全性越高，但并发能力越低；粒度越细并发越高，但管理成本也更高。我们的设计也是逐步优化的，V1 按节目维度加锁，整个节目下单串行，实现简单但吞吐较低；V2 细化到票档维度，同一节目不同票档可以并行下单，并发能力提升。用户维度锁主要用于限制同一用户重复操作，比如下单防重复提交、注册手机号防重；订单号维度锁用于支付、取消等订单状态流转，保证同一个订单同一时间只有一个状态修改操作。所以锁粒度不是固定选择，而是根据具体资源的竞争范围决定。

------

**Q：加锁失败走什么策略?为什么选择快速失败而不是等待?**

A：我们主要采用快速失败策略。注解锁默认等待一定时间，超过等待时间仍未获取到锁就直接返回异常；防重复提交场景使用非阻塞获取，抢不到立即提示请求频繁。选择快速失败主要是因为抢票场景流量具有突发性，如果大量请求等待锁，会占用线程资源，持锁方异常时还可能造成请求堆积。快速失败可以让系统快速释放压力，由上层决定重试或者提示用户，避免因为锁竞争导致整体雪崩。

------

**Q：锁 key 命名需要注意什么?怎么避免不同业务互相影响?**

A：锁 key 的核心要求是同一资源必须生成相同的锁名，不同业务不能发生冲突。我们的锁名称采用统一规范，由环境前缀、业务名称和业务 key 组成。环境前缀避免不同环境之间互相影响，业务名称区分不同锁用途，业务 key 使用真正唯一的资源标识，例如订单号、用户 ID。注解式和编程式加锁都复用同一套命名规则，保证不同入口针对同一资源时能够竞争同一把锁。

------

**Q：分布式锁哪些真实场景会失效?你们如何处理这种风险?**

A：主要关注两类风险。一类是 Redis 主从切换导致锁丢失，锁还没有同步到从节点时主节点宕机，从节点提升后可能不存在原来的锁；另一类是 JVM 长时间停顿，例如 Full GC，导致持锁线程无法及时续期，锁提前过期后其他请求进入。我们不会认为 Redis 锁是绝对强一致方案，而是作为并发控制手段使用。关键业务还会结合幂等、状态机校验和补偿机制兜底，比如支付和取消都会校验当前订单状态，即使锁异常失效，也不会重复执行非法状态转换。

------

**Q：锁持有时间和下游超时(DB/Feign)怎么配合?怎么设置 leaseTime?**

A：锁时间需要覆盖完整业务执行周期，包括自身逻辑、数据库操作以及远程调用耗时。如果显式设置 leaseTime，需要根据下游最坏耗时估算，比如 Feign 超时时间、重试次数，再加上自身执行时间和一定缓冲，否则可能业务还没完成锁已经释放。反过来，下游超时时间过长也会导致锁持有时间变长，降低并发能力。因此大部分场景我们使用 Redisson 看门狗自动续期，让锁跟随业务生命周期；只有需要明确控制最大占用时间的场景才使用固定 leaseTime。
