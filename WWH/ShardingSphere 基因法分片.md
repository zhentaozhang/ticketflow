# ShardingSphere 基因法分片

## 动机与选型

**Q：你们的订单数据量/QPS 到什么程度才决定分库分表？评估依据是什么？**

A：我们这个项目不是因为已经达到线上大规模数据量才被迫分库分表，而是为了按照互联网交易系统的设计方式，主动实践高并发场景下的水平扩展方案。主要考虑两个问题：一方面订单属于持续增长的流水数据，单表数据量变大后，索引维护、查询效率和数据迁移都会受到影响；另一方面票务场景存在开票瞬间的流量峰值，单库写入能力会成为瓶颈。所以我们提前引入分库分表，重点实践分片设计、精准路由以及一致性处理等问题。

------

**Q：分库分表之前考虑过其他方案吗（分区表、归档、读写分离）？为什么最终走了分库分表？**

A：这些方案解决的问题不同。分区表主要优化单表管理，但无法突破单库写入能力；归档主要解决历史数据增长，对瞬时写压力帮助有限；读写分离主要优化查询压力，而票务系统核心挑战是高峰写入。因此我们选择分库分表，希望同时提升数据容量和写入扩展能力。当然真实业务中是否分库分表需要结合数据规模和成本评估，我们这个项目主要是为了实践大型交易系统中的架构方案。

------

**Q：你们是垂直拆分还是水平拆分？业务服务上是怎么配合拆分的？**

A：两种拆分都有实践。垂直拆分按照业务领域划分服务和数据库，比如用户、节目、订单、支付独立管理；水平拆分主要针对订单表，通过分库分表降低单库压力。订单域设计为 2 库 8 表，并使用基因法保证 user_id 和 order_number 两种查询入口能够定位到同一个分片。业务流程上，节目服务负责库存和订单号生成，订单号生成时嵌入用户路由信息，再通过 Kafka 异步通知订单服务完成建单。

------

**Q：分库分表后哪些事情变难了（跨片查询、分页、事务）？你们实际遇到哪些？**

A：分库分表提升扩展能力的同时，也增加了系统复杂度。主要包括三个方面：第一，没有分片键的查询无法精准路由，需要避免广播查询，所以核心业务查询都设计成携带分片键；第二，跨分片分页需要结果归并，因此用户订单列表按照 user_id 路由，保证单用户查询只访问一个分片；第三，跨库事务无法依赖本地事务解决，所以采用最终一致性方案，通过消息、补偿和幂等机制保证状态一致。

------

**Q：为什么选择 ShardingSphere，而不是 MyCat？两者分片原理有什么区别？**

A：主要区别在架构模式。ShardingSphere JDBC 模式将分片逻辑放在应用侧，应用直接连接数据库，减少代理层开销，也避免代理节点成为瓶颈；MyCat 属于代理模式，SQL 需要经过中间代理节点转发。另外我们的项目需要实现基因法这种自定义分片算法，ShardingSphere 提供 SPI 扩展能力，可以方便实现自定义路由逻辑，所以更符合我们的设计需求。

## 分片键与基因法核心

**Q：订单表为什么选用户维度做分片?换节目维度会怎样?**

A：主要考虑查询场景和数据分布。C 端最高频的是"我的订单"查询，按 user_id 分片可以让同一个用户的订单集中在一个分片，查询时直接精准路由。同时订单从创建、支付到取消、退款，大部分生命周期操作都围绕用户和订单展开，集中到同一分片也方便本地事务处理。如果按节目维度分片，热门节目开票时大量请求会集中到同一个分片，容易产生热点；用户查询自己的订单时还需要跨分片聚合。所以用户维度更适合作为订单主表分片键。

------

**Q：为什么同时使用 user_id 和 order_number 两个分片键?分别解决什么问题?**

A：两个分片键对应不同业务入口。user_id 主要支撑"我的订单"列表这类用户维度查询；order_number 主要支撑订单详情、支付回调、超时取消等场景，因为这些请求通常只能拿到订单号。为了保证两个查询入口都能精准路由，订单号生成时会携带 user_id 的基因信息，让两个分片键最终落到同一个分片。关联表一般按 order_number 分片，因为它们通常都是通过订单号关联查询。

------

**Q：什么是基因法?为什么不用简单的取模分片?**

A：基因法的核心思想是让业务 ID 自身携带分片信息。我们在生成订单号时，把 user_id 的部分低位编码进去，使订单号和 user_id 共享相同的路由基因，后续根据任意一个字段都可以计算出相同分片。普通取模分片的问题在于 user_id 和 order_number 是两个不同值，两个字段取模结果无法保证一致，只能额外维护映射表解决，这会增加存储和一致性成本。基因法把映射关系提前编码到 ID 中，查询时直接计算即可。

------

**Q：订单号里怎么嵌入 userId?这个动作的本质是什么?**

A：本质是位段编码。标准雪花 ID 的低位通常用于序列号，我们将部分序列位让出来，把 user_id 的低位写入订单号。这样订单号除了保证唯一性之外，还额外携带了路由信息，后续可以直接通过位运算得到分片位置。代价是订单号生成逻辑必须统一管理，不能让外部随意生成订单号。

------

**Q：为什么选择 userId 的低位作为基因，而不是高位?**

A：主要有两个原因。第一，需要保证订单号和 user_id 的对应位一致，而基因位固定在订单号低位，因此必须取 user_id 的低位。第二，低位变化更加充分，分布通常更均匀；高位往往包含时间或者增长趋势信息，同一时间产生的数据可能高位接近，容易导致分片倾斜。所以使用低位既保证路由一致，也有利于数据均衡。

------

**Q：如果订单号没有携带基因，会有什么问题?**

A：订单号依然可以作为分片键计算路由，但它和 user_id 的路由结果无法保证一致。同一个用户的订单可能分散在不同分片，查询"我的订单"时只能广播查询所有分片，再进行结果合并。如果想同时支持 user_id 和 order_number 精准路由，就需要额外维护 user_id 到 order_number 的映射关系。因此基因法本质上是用生成阶段增加一点编码成本，换取查询阶段无需额外映射。

------

**Q：按 userId 查订单列表、按 orderNumber 查详情，为什么都能落到同一个分片?**

A：因为两个字段在生成阶段已经绑定。订单号生成时会嵌入 user_id 的低位，因此 user_id 和对应订单号拥有相同的基因位。分片算法只需要读取这部分位信息，无论输入的是 user_id 还是 order_number，计算出的分库和分表结果都一致。所以两个查询入口都可以精准定位同一个物理分片，不需要广播查询。

------

**Q：跨库查询/读扩散的代价是什么?基因法为什么不需要映射表?**

A：没有分片键时，查询需要发送到所有分片执行，再对结果进行归并，分片数量越多，网络请求、数据库压力和结果合并成本越高。如果使用映射表，需要先根据订单号查询映射关系，再根据 user_id 路由，多一次 IO，同时还要保证映射数据和订单数据的一致性。基因法直接把路由关系编码在订单号中，查询时一次位运算即可定位分片，避免了额外查询和维护成本。

------

**Q：为什么索引表或者冗余映射方案可以不做?基因法的优势是什么?**

A：因为订单号本身就是自描述的，生成时已经包含了路由信息，不需要额外维护一张动态映射表。映射方案需要额外存储、查询和处理一致性问题，而基因法把这些关系固化在 ID 生成阶段。它的代价是订单号生成必须统一控制，并且基因位宽决定了未来可支持的分片规模，但对于订单这类内部生成 ID 的场景，这种交换是值得的。

## 位运算与约束

**Q：为什么分片数必须是 2 的幂?如果配置成 3、5 会出什么错?**

A：因为我们的路由算法基于位运算，而位运算天然要求分片数量是 2 的幂。分表索引直接取基因位低位，分库索引再取高位，本质都是按固定 bit 位切分；只有分片数是 2 的幂，才能保证位段和索引范围一一对应。如果配置成 3、5，位段无法均匀划分，会导致部分分片无法命中或者路由结果异常。所以我们在初始化阶段做配置校验，发现非 2 的幂直接失败，避免产生错误路由。

------

**Q：分库索引为什么要扣掉表基因位再取高位?位段是怎么分配的?**

A：因为同一个基因位需要同时决定库和表，所以必须提前划分不同位段，避免冲突。我们的设计是低位负责分表，高位负责分库，计算分库索引时先跳过已经使用的分表位，再从剩余位中取分库信息。这样同一个订单号可以同时得到库索引和表索引，而且两者互不影响。例如 2 库 8 表时，低 3 位决定表，高 1 位决定库；扩容时只需要增加使用的位段，不需要修改订单号生成逻辑。

------

**Q：位运算相比 hashCode 取模，分布和性能好在哪?**

A：性能上，位运算本质是移位和与操作，比取模计算更轻量，在高频路由场景下开销更低。更重要的是位运算可以精确控制使用哪些 bit，把同一个 ID 中不同位置的信息分别解析成分库和分表索引，这是普通 hash 取模无法做到的。hash 主要解决均匀分布问题，但无法保证 userId 和 orderNumber 两个业务字段之间的路由关系一致。

------

**Q：基因位你们预留了几位?最大支持多少分片?预留逻辑背后是什么考虑?**

A：我们预留了 6 位基因空间，可以支持最多 64 种分片组合，当前设计满足 8 库 8 表。预留的目的主要是为了扩容时不修改订单号生成规则，未来增加分片数量时只调整路由解析逻辑即可。代价是需要从雪花序列中让出部分位，因此订单号单毫秒内可生成数量会下降，但对于票务下单场景已经足够。

------

**Q：未来从 2 库 4 表扩到 8 库 8 表，生成逻辑要不要改?为什么?**

A：不用改。基因信息在订单号生成阶段已经写入，生成逻辑只负责产生带路由信息的 ID，具体如何解析这些位由分片规则决定。扩容时主要变化的是路由配置和存量数据迁移，需要按照新的分片规则重新计算目标位置，把历史数据批量迁移过去。迁移过程采用幂等写入和分批执行，支持失败重试，避免一次性切换带来的风险。

## 倾斜与查询适配

**Q：基因法会不会数据倾斜?低流量阶段你们实际发现过什么问题、怎么修的?**

A：理论上基因法分布是均匀的，因为路由取的是 userId 低位，用户量越大越接近随机分布。但在冷启动阶段我们发现过局部热点：低流量时订单生成数量少，如果雪花序列号每次从固定值开始，订单号取值范围比较集中，导致部分基因位命中偏高。针对这个问题，我们调整为序列号随机起步，让订单号分布更离散；同时增加分片命中统计，周期观察各库表的数据和流量分布，提前发现热点。

------

**Q：无分片键的查询会怎么样?你们业务里怎么保证查询都带上分片键?**

A：没有分片键的查询只能广播到所有分片，再进行结果归并，随着分片数量增加，查询压力会线性放大。业务上尽量避免这种情况：C 端查询天然携带分片键，订单列表按 userId 路由，详情、支付、取消按 orderNumber 路由；管理后台这类复杂查询，会先通过辅助索引定位订单号，再进行精准路由；只有低频统计类场景才允许广播查询。

------

**Q：一个用户疯狂下单会不会把他的分区打热?热分片怎么发现?**

A：单个用户通常不会造成分片热点，因为订单生成和接口频率都有上限。真正的风险是多个高频用户恰好落在同一个分片，造成局部压力集中。我们主要通过分片监控发现，比如统计各库表的数据量、请求量和命中比例，如果某个分片长期明显偏高，就进一步分析用户分布和业务流量。冷启动阶段出现的局部热点，则通过序列号随机起步进行了优化。

------

**Q：同一查询同时带 order_number 和 user_id 时，你们做了防呆，为什么?防的是什么?**

A：因为基因法要求 userId 和 orderNumber 计算出来的分片必须一致，所以查询时如果同时带两个分片键，我们会分别计算路由结果，如果不一致直接报错。防的是错误数据或者错误调用导致的静默错路由。如果只选择其中一个条件继续查询，可能查不到真实数据，但问题不会暴露，后续排查成本很高。通过提前校验，可以快速发现数据不一致或调用错误。

## ID 生成、迁移与其他

**Q：分库分表后全局唯一 ID 怎么生成?为什么不用 UUID?**

A：我们设计了统一的分布式 ID 生成方案。业务主键使用雪花类 ID，订单号在此基础上增加基因位编码路由信息，机器号通过 Redis 进行分配，并提供异常降级方案。没有选择 UUID，是因为 UUID 是 128 位随机字符串，无序且占用空间大，作为 InnoDB 主键容易造成页分裂，同时也无法携带分片信息。雪花 ID 是 64 位 long 类型，趋势递增，并且可以预留业务位，更适合和分库分表结合。

------

**Q：你们在标准雪花上改了什么?为什么订单号的序列号位宽和主键 ID 不一样?**

A：订单号基于标准雪花做了三处调整：第一，把部分序列号位让给 userId 基因，用于路由；第二，增加时钟回拨处理，避免生成重复 ID；第三，序列号改为随机起步，减少低流量阶段的分片集中。主键 ID 和订单号职责不同，所以位宽设计不同。主键只需要保证唯一和高吞吐生成，可以保留完整序列位；订单号还需要承载路由信息，因此必须牺牲部分序列空间给基因位。

------

**Q：时钟回拨会导致什么?你们的容忍策略是什么?**

A：雪花算法依赖时间递增，如果系统时间回退，可能出现相同时间戳和序列号组合，从而生成重复 ID。我们的处理分两种情况：小范围回拨认为是正常时钟漂移，等待时间追平后继续生成；大范围回拨说明机器时间异常，直接拒绝生成并报警，宁可请求失败，也不能产生重复 ID。

------

**Q：同一毫秒订单号耗尽会怎样?为什么新毫秒序列号要随机起步?**

A：当单毫秒内序列号达到上限时，生成器会等待下一毫秒继续生成，不会继续产生冲突。序列号随机起步主要是为了优化低流量场景：如果每次都从固定值开始，订单号低位会集中在固定范围，导致基因路由出现局部偏斜；随机起步可以让订单号分布更离散，减少冷启动阶段的热点。

------

**Q：数据迁移你们怎么做的?为什么需要强制路由(忽略分片算法)?**

A：数据迁移由独立迁移服务负责，按照旧分片逐批扫描数据，根据新的分片规则计算目标位置，目标位置不变的数据直接跳过，需要迁移的数据批量写入目标分片后再删除源数据。整个过程支持限速、预演、幂等写入和失败重试。迁移时必须使用强制路由，因为正常分片算法只能根据当前规则计算目标表，而迁移的目的正是改变数据所在位置，如果仍走普通路由会无法精确控制数据迁移路径。

------

**Q：订单表分库分了，关联表(票档、购票人)怎么保证和订单同库?**

A：核心是让关联表使用和订单一致的分片键。购票人、订单记录等关联表都携带 order_number，并按照订单号分片，因此同一个订单的数据天然落在同一分片。同时在 ShardingSphere 中配置绑定表关系，避免关联查询时产生跨库 join。对于跨业务域的数据，比如支付账单，也按照订单号保持分片一致，通过接口完成跨域访问。

------

**Q：分库后的分布式事务你们真实落地了吗?哪些场景用了什么?**

A：我们没有在核心下单链路引入 Seata 这类强一致分布式事务，因为抢票场景对性能要求高，全局锁和协调开销会影响吞吐。实际采用的是本地事务保证单库一致性，跨服务场景通过消息、状态机和补偿保证最终一致。比如异步建单失败会释放锁定资源并恢复库存，订单超时未支付通过延迟任务取消并回补，支付回调通过幂等控制避免重复更新。对于极端异常情况，通过定期对账发现并修正数据。
