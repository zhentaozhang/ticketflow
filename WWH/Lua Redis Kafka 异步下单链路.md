# Lua + Redis + Kafka 异步下单链路

## 链路总览

**Q：一次下单从进入到出结果,完整链路怎么走的?**

A：整个链路分为同步受理和异步落库两部分。用户提交下单请求后，先经过参数校验和业务校验，然后执行 Redis Lua 脚本，在 Redis 内原子完成余票校验、座位锁定、库存扣减和流水记录。Lua 执行成功后，节目服务生成订单号，将建单消息发送到 Kafka，同时投递延迟取消消息，然后立即返回订单号给用户。后续由订单服务消费 Kafka 消息完成订单、购票人等数据落库，用户通过订单状态查询获取最终结果；如果超过支付时间未完成支付，则由延迟任务触发取消并回补库存。

------

**Q：哪些环节同步、哪些异步?为什么这么划分?**

A：同步部分主要负责"能不能受理"，包括参数校验、业务校验、Redis Lua 扣减库存以及 Kafka 消息发送确认，这些操作耗时短，并且直接决定下单是否成功。异步部分主要是数据库落库、超时取消、对账等操作，这些涉及多表事务和慢 IO，不适合阻塞用户请求。整体设计原则是请求线程只完成资源预占和消息投递，把慢写操作异步化，让接口响应时间主要取决于 Redis 操作和消息发送，从而提升高并发场景下的吞吐能力。

------

**Q：如果全同步下单,高并发下会发生什么?**

A：全同步模式下，请求线程需要等待订单创建、购票人写入、订单记录保存等数据库操作完成后才能返回。高并发情况下，数据库写入和事务耗时会导致大量请求长时间占用线程池，线程资源快速耗尽，新请求只能排队等待甚至超时。同时数据库连接和写压力也会集中增加，最终导致整体吞吐下降。异步化的核心就是把慢操作移出请求链路，避免数据库成为用户请求的同步瓶颈。

------

**Q：用户怎么知道下单成功?为什么轮询方案能接受?**

A：下单接口会同步返回预生成的订单号，代表请求已经被系统受理，但此时订单可能还处于异步创建中。用户拿订单号查询订单状态，订单服务消费 Kafka 消息完成落库后，状态会从创建中变为待支付。轮询方案可以接受的原因是建单延迟通常较低，用户能够快速看到结果，同时相比让请求一直等待数据库写入完成，轮询把等待时间从同步链路中移出，提高了接口响应速度。对于抢票这类场景，用户本身就会持续关注订单状态，因此轮询成本可控。

------

## Lua 原子性与防超卖

**Q：库存扣减为什么用 Lua?Redis 单线程执行 Lua 为什么天然原子?**

A：扣库存不是一个简单命令，而是包含余票校验、座位校验、锁定、扣减等多个步骤，这些操作必须作为一个整体执行，不能执行到一半被其他请求插入。Redis 的 Lua 脚本会作为一条命令提交到 Redis 单线程执行模型中，脚本执行期间其他命令都会排队等待，不会穿插执行。因此脚本内部的多个操作对外表现为一个原子操作，要么全部成功，要么全部失败。同一个票档的扣减也因此天然串行，不会出现并发交错导致的数据问题。

------

**Q：为什么不用 MULTI/EXEC 事务?差在哪?**

A：MULTI/EXEC 只能保证命令按顺序执行，但它不支持根据执行结果动态控制后续逻辑，也不会自动回滚。我们的扣减流程需要先判断余票、座位状态，再根据结果决定是否继续执行，同时失败时还需要返回具体业务错误码，这属于带业务逻辑的控制流。Lua 脚本可以在 Redis 内完成条件判断、流程控制和统一返回结果，因此比 MULTI/EXEC 更适合库存扣减这种场景。

------

**Q：你们的 Lua 脚本一次做了几件事(校验余票/座位/价格+锁定+扣减+写流水)?为什么必须在一个脚本里?**

A：Lua 脚本主要完成六个步骤：校验票档余票是否充足，校验座位是否存在且未被占用，校验请求价格和 Redis 中的真实价格是否一致，将座位从未售状态移动到锁定状态，扣减对应余票，最后写入扣减流水。V5 版本还增加了幂等校验。之所以全部放在一个脚本中，是因为这些操作存在严格依赖关系，如果拆成多个 Redis 请求，校验和扣减之间会产生并发窗口，多个请求可能同时通过校验后重复扣减。放入同一个 Lua 脚本后，整个过程成为一个原子动作，保证一次下单要么完整占用资源，要么完全失败。

------

**Q：余票"先查后扣"分成两步会怎样?超卖是怎么发生的?**

A：超卖的根本原因是查询、判断、修改之间存在并发窗口。比如当前余票只有 1 张，两个请求同时查询到库存充足，然后都执行扣减，最终就会出现卖出超过实际库存的情况。座位也是类似，两个请求同时判断某个座位未售，然后都进行锁定，就会导致同一个座位被出售两次。Lua 把查询、判断、修改合并成一个原子过程，消除了中间窗口，保证每次扣减看到的都是最新状态。

------

**Q：座位锁定怎么实现?未售与已锁之间怎么流转?**

A：座位状态在 Redis 中划分为未售、已锁、已售三个区域，每个区域保存对应座位信息。下单时 Lua 脚本会将座位从未售区域删除，同时写入已锁区域，状态变更在同一个原子操作中完成。支付成功后，座位从已锁转为已售；如果订单超时取消，则从已锁回滚到未售。通过这种状态流转设计，一个座位同一时间只会处于一种状态，查询状态时直接判断所在区域即可。

------

**Q：价格为什么也放脚本里校验?应用层校验有什么漏洞?**

A：主要是防止客户端传入非法价格。如果只在应用层校验价格，再单独执行扣减，两者之间存在时间窗口，可能出现校验通过但实际扣减时数据已经变化的问题。同时请求中的价格本身是不可信的，真正的价格应该以 Redis 中缓存的权威数据为准。将价格校验放入 Lua 后，价格验证和锁座扣减在同一个原子流程中完成，避免绕过和数据不一致。

------

**Q：脚本失败返回什么?错误码的粒度你们是怎么设计的?**

A：脚本统一返回结果对象，成功返回成功码以及锁定的座位信息，失败返回具体错误码。错误码按照业务原因拆分，例如余票不足、票档不存在、座位不存在、座位已锁定、座位已售出、价格不一致等。这样前端可以展示准确提示，应用层也可以根据错误类型做不同处理，比如座位竞争失败可以重试，而价格错误或库存不足属于直接失败。

------

**Q：脚本里写的扣减流水(purchase record)是干什么的?之后谁会消费它?**

A：扣减流水主要用于记录 Redis 中资源变化过程，包括余票变化、座位状态变化以及对应订单信息。后续由对账任务消费这些流水，将 Redis 中的扣减记录和数据库订单进行比对，发现 Redis 已扣减但数据库未落库、或者数据库有订单但 Redis 状态异常等情况时进行补偿。它的作用是保证库存链路可追踪，让最终一致性问题能够被发现和修复。

------

**Q：脚本执行期间其他请求能看到半成品状态吗?**

A：看不到。Lua 脚本执行期间，Redis 单线程会阻塞其他命令执行，其他请求只能等待脚本完成。因此外部请求只能看到脚本执行前的完整状态，或者执行后的完整状态，不会看到"已经锁座但还没扣库存"这类中间状态。这也是 Lua 能保证库存操作原子性的核心原因。

------

**Q：V5 把幂等也并进了脚本,相比之前独立幂等控件,你们省掉了什么、解决了什么?**

A：V4 中幂等控制和库存扣减是两个独立流程，需要先检查幂等标记，再执行 Lua 扣减，中间存在多次 Redis 交互和并发窗口。V5 将幂等校验放到 Lua 脚本最前面，和库存校验、座位锁定一起作为一个原子操作。这样减少了一次独立幂等请求，同时解决了"幂等检查通过但扣减前被其他请求插入"的问题，让重复提交和库存扣减在同一个原子边界内处理。

------

## 幂等设计

**Q：幂等标记 SETNX 的原理?TTL 窗口怎么设?为什么窗口内重发直接拒绝?**

A：SETNX 就是"只有 key 不存在时才能设置成功"，我们利用这个特性做一次性标记。请求进入时先设置幂等 key，成功说明这是窗口内第一个请求，可以继续执行；失败说明已经有相同请求正在处理或者已经处理过，直接拒绝。标记带 TTL，窗口期内存在，窗口结束后自动释放，所以同一个操作在窗口内只会生效一次，窗口过后可以重新提交。TTL 窗口按照"从请求进入处理到最终生效"的最长耗时来确定，比如下单防重的幂等窗口设置为 10 秒，需要覆盖请求受理、消息投递到订单落库的整个链路。太短会导致请求还没处理完成标记就过期，重复请求可能再次进入；太长又会影响用户正常重试。窗口内重发直接拒绝，是因为第一次请求已经被系统受理，再执行一次会导致重复扣减、重复建单，不符合幂等语义。

------

**Q：请求失败时幂等标记怎么处理?为什么失败和成功要区分对待?**

A：成功和失败代表两种不同的业务状态，幂等标记应该只表示"这个操作已经成功执行过"。成功后写入标记，后续相同请求可以安全拒绝；失败时不应该保留标记，必要时主动释放，让用户可以重新提交。我们独立幂等控件是在业务成功后才写入标记，异常情况下不会写入；V5 脚本里，校验或者扣减失败时会先删除幂等标记，再返回具体错误码。这样可以区分"已经成功处理"和"本次执行失败"，避免一次临时异常导致用户在 TTL 窗口内无法重试，也不会把失败请求误认为重复请求。

------

**Q：幂等和防超卖分别防的是哪类问题?能互相替代吗?**

A：幂等和防超卖解决的是两个不同维度的问题，不能互相替代。幂等防的是"同一个请求重复执行"，比如用户连续点击、Kafka 消息重复投递、支付回调重复通知，它通过幂等标记保证同一个业务只生效一次；防超卖防的是"不同请求并发竞争同一份资源"，比如多个用户同时购买同一个票档的余票，它通过 Lua 原子扣减保证库存不会因为并发竞争卖超。两者缺一不可：只有防超卖，没有幂等，同一个请求重复执行虽然不会导致库存超卖，但会重复扣减；只有幂等，没有防超卖，不同用户之间依然可能同时抢占同一份库存。所以 V5 把两者放进同一个 Lua 脚本里，一个负责幂等守卫，一个负责原子扣减，在同一个原子边界内解决重复请求和并发竞争问题。

------

## Kafka 削峰解耦

**Q：Kafka 在链路里承担什么?它靠什么机制削峰?**

A：Kafka 在链路里承担的是"异步建单"的作用，把用户请求受理和数据库落库两个阶段解耦。节目服务执行 Lua 扣库存成功后，将建单消息发送到 Kafka，订单服务按照自身消费能力异步完成数据库落库。削峰的核心是利用生产者和消费者处理速度的不一致来做缓冲：抢票高峰期请求量瞬间上涨，但 DB 多表写入和事务提交能力有限，Kafka 可以暂存消息，把瞬时流量转换成稳定的消费流，数据库最终只承受消费者能够处理的速率，而不是直接承受入口流量。同步调用无法做到这一点，因为请求线程会一直等待慢操作完成，导致线程池被占满。

------

**Q：你们怎么保证消息不丢?生产端、Broker、消费端三个层面分别怎么做?**

A：消息可靠性从生产端、Broker、消费端三个层面保证。生产端开启消息确认机制，等待 Broker 副本确认成功，同时配置失败重试和幂等生产者，避免网络抖动导致重复发送；如果发送最终失败，说明订单没有进入异步链路，需要回滚 Redis 中已经锁定的座位和扣减的余票，让用户重新提交。Broker 侧通过消息持久化和副本机制保证节点故障时消息不会丢失，只有消息写入副本后才认为发送成功。消费端主要通过幂等保证可靠处理，因为 Kafka 默认是至少一次语义，消息可能重复但不能因为重复导致业务错误；消费失败时会留下失败记录，由补偿和对账任务进一步处理，避免异常被静默吞掉。

------

**Q：重复消费订单消息会怎样?消费端靠什么幂等?**

A：重复消费最直接的问题是同一个订单被重复创建，导致重复落库甚至重复占用资源。我们消费端主要通过两层幂等保证：第一层是业务层防重，以订单号作为唯一标识，相同订单号在幂等窗口内只允许处理一次；第二层是数据库唯一约束兜底，消费建单前根据订单号检查，如果订单已经存在就直接拒绝重复创建。这样即使 Kafka 因为 offset 提交失败或者消费异常导致消息重复投递，同一个订单最终也只会落一份数据。因为 Kafka 本身保证的是至少一次投递，所以消费端幂等是必须补充的一层。

------

**Q：消费速度跟不上生产怎么办?瓶颈可能在哪、怎么调?**

A：消费速度跟不上生产时，首先表现为 Kafka 消息积压，消费延迟增加。瓶颈通常不在 Kafka，而是在消费者后面的业务处理能力，尤其是订单落库涉及多表写入和事务提交。优化方向主要有两个：一是提高消费并行度，通过增加 topic 分区数和消费者实例数量提升吞吐；二是降低单条消息处理耗时，比如减少数据库交互、优化批量写入。实际处理时需要根据积压量和业务一致性要求决定策略，不能简单丢消息。V5 版本中 Redis 是库存权威，积压消息不会直接丢弃，而是继续消费建单，异常情况通过最终一致性补偿处理，避免出现库存已经扣减但订单永久丢失的问题。

------

**Q：订单消息的分区/顺序需要考虑吗?同一用户多单的顺序重要吗?**

A：订单消息本身不要求强顺序，因为不同订单之间没有业务依赖。每个订单都有独立订单号和独立资源，同一个用户连续提交多个订单时，先创建哪一个不会影响最终结果，所以我们优先保证吞吐，不额外牺牲并行能力。如果是同一个资源必须严格按照操作顺序处理的场景，比如库存扣减、状态流转，这类顺序问题不交给 Kafka，而是在 Redis Lua 或业务状态机里通过原子操作保证。因此订单 topic 不指定用户作为分区 key，是基于业务特点做的取舍。

------

**Q：为什么把"创建订单"做成 MQ 消费而不是同步 Feign?失败重试怎么做?**

A：同步 Feign 创建订单的问题是请求线程必须等待订单服务完成数据库写入，高并发情况下慢 SQL、多表事务和网络调用都会占用大量线程，导致入口服务吞吐下降，同时服务之间强耦合，一个服务异常容易影响整个链路。改成 MQ 消费后，节目服务只负责快速受理和发送消息，订单服务作为独立消费者异步落库，既能削峰，也实现服务隔离。失败处理分两类：生产端发送失败时，说明请求没有进入建单链路，需要回滚 Redis 中已经锁定的资源；消费端失败时，不能简单忽略，需要记录异常并通过补偿任务恢复一致性。V5 进一步调整为 Redis 作为库存权威，消息积压不直接丢弃，通过持续消费和最终一致性机制保证订单状态最终收敛。

------

## 延迟任务与超时取消

**Q：扣了库存用户不付钱,什么时候取消?方案为什么选延迟队列?**

A：下单成功后我们会投递一条延迟消息，2 分钟后到期触发检查：订单还是未支付就取消，回补座位和余票。为什么用延迟队列而不是别的：这个场景的语义是"每个订单到点检查一次"，延迟队列按单精准触发，到期才出队，不需要定时扫全表；而 DB 轮询要定时扫描"未支付且超时"的订单，数据量大时每次都扫全表，压力大、延迟也不精准。延迟队列让"每个订单只在自己该被检查的时刻被处理"，实现和成本都更划算。

------

**Q：延迟任务有哪些实现(时间轮/DB轮询/RDelayedQueue/Kafka) 你们怎么对比后定的?**

A：主要对比了四类。时间轮是内存结构，适合短延迟和单机，不支持持久化，进程一挂任务就丢，跨实例还要自己搞分布式时间轮，太复杂；DB 轮询实现最简单，但订单量大时全表扫描压力大，触发延迟取决于扫描间隔，不精准；Kafka 本身不支持延迟，要么按延迟时间拆多个 topic，要么消费端判断未到期再放回去，积压管理和复杂度都不划算；RDelayedQueue 基于 Redis，消息持久化、天然分布式、到期精准触发。我们本来就有 Redis 依赖，选 RDelayedQueue 成本最低，还利用它的持久化和分布式能力，不需要引入新组件。

------

**Q：Redisson 延迟队列底层原理?凭什么到点才出队?**

A：RDelayedQueue 内部用两个结构：一个有序集合存延迟消息，分值就是到期时间戳；一个普通队列存已到期的消息，再配合发布订阅。入队时把消息按"当前时间加延迟时长"作为分值写进有序集合；后台有个机制持续盯着有序集合的队首，队首没到期就等待，一旦队首的到期时间到了，就把它从有序集合移到普通队列，并通知等待的消费者。所以"到点才出队"靠的是按到期时间排序、每次只检查队首：队首不到期，后面的更不可能到期，直接等待，不会提前取出任何消息。消费者阻塞在普通队列上，被通知后才取。

**Q：你们为什么在 RDelayedQueue 外包了一层?分区设计解决了什么?**

A：包一层主要是三个原因：统一发送入口、按 topic 隔离、一个 topic 内部做分区。我们把一个 topic 拆成多个物理分区，每个分区对应一个独立的 RDelayedQueue，发送时轮询选一个分区写入，消费端也按相同的分区数建对应的消费者。分区解决两个问题：一是把延迟消息的写入分散到多个 Redis key 上，避免所有消息挤在同一个有序集合造成热点；二是隔离——某个分区消费慢或者出问题，只影响这一个分区，不会拖垮整个 topic 的所有消息。外层还统一管 topic 和分区的生命周期，业务方只调用一个发送方法，不感知底层结构。

**Q：延迟消息会丢吗?发送失败、消费失败、进程宕机,你们各自怎么兜底?**

A：分三个环节看。发送环节：发送前先把消息内容写进消息日志库，再投递，发送失败会把日志状态标记为失败，留给对账；线程池如果饱和，降级成同步发送，不让消息丢。消费环节：消费者处理失败会留下消费记录，取消逻辑本身是幂等的，订单状态校验加锁，重复消费或重投不会造成重复回补。进程宕机环节：延迟数据存在 Redis 的有序集合和队列里，Redis 不丢，实例重启后能恢复消费；消息日志在数据库，也可以对账兜底。整体思路是发送留日志、消费做幂等、存储靠 Redis，三层配合把丢失概率压到很低。

**Q：取消订单后库存怎么回补?和下单脚本的扣减怎么对应?**

A：取消订单时，订单状态更新完成后会对 Redis 做一次反向操作：把座位从已锁区移回未售区，把余票按扣减的数量加回去，这正是下单脚本的镜像——下单脚本是未售到已锁加余票减，取消脚本是已锁回未售加余票增，用的是同一套 Lua 反向脚本，保证原子。DB 侧节目数据也会同步更新：老版本走延迟队列异步落库，V4/V5 走 Feign 同步更新，并且都做了幂等，重复取消不会重复回补。这样用户 2 分钟不付款取消后，这些库存可以立刻被其他用户买走。

**Q：取消和支付"撞车"怎么防?你们用状态机还是别的手段?**

A：靠三层配合。第一层是同订单号的分布式锁，取消和支付回调都用同一把锁，同一订单的这两个操作只能串行执行，不可能同时进；第二层是状态机校验，每个操作进来先查订单状态，已取消的订单拒绝支付、已支付的订单拒绝取消，状态流转只有合法路径；第三层是幂等，两个入口都标了防重复，重复的回调或取消不会重复生效。撞车场景下谁先拿到锁谁先改状态，后到的那个被状态校验拦下——比如支付先完成，取消进来发现已支付就拒绝；取消先完成，支付回调发现已取消就发起退款而不是继续支付。所以锁保证串行、状态机保证合法、幂等保证不重复。

------

**Q：延迟机制除了超时取消还用在哪?节目数据延迟操作解决什么?**

A：还有一个是"节目数据操作"的延迟队列，支付成功或取消订单后，延迟 1 秒触发对节目侧数据的更新，比如座位标记已售、余票落库。它解决的问题是：老版本链路里这些节目侧数据变更不放在订单状态更新的同步事务里做，而是延迟异步执行，把跨服务的数据更新从订单主流程里剥出来，缩短事务、降低耦合；延迟 1 秒还给在途的下单操作留了缓冲窗口，避免和正在进行的扣减直接竞争。V4/V5 后来改成了同步 Feign 更新，是另一条路径。整体上延迟机制承担了"超时决策"和"错峰落库"两类职责。
