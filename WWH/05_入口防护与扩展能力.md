# 主题五：入口防护与扩展能力（网关限流 + 验证码防刷 + 灰度发布 + ES 搜索） —— 面试深挖分析

> 基于"业务问题 → 技术方案 → 设计原因 → 实现方式 → 遇到问题 → 优化方案 → 极端情况处理"链路。
> 每个技术点按「是什么 / 为什么 / 怎么办」三层组织，代码锚点均经 codegraph 核实。

---

## 1. 项目背景

### 业务场景
抢票系统的高并发压力从**入口**就开始了：开票瞬间大量请求涌入网关，可能来自正常用户、脚本刷票、恶意攻击。入口层扛不住，后面的服务再优化也白搭。

入口层需要解决四类问题：
- **流量超载**：瞬时请求量超过系统承载，需要快速失败保护；
- **恶意刷接口**：脚本高频调用登录/下单/验证接口，需要识别并拦截；
- **发布风险**：新版本上线直接全量切流量，出问题影响面大；
- **检索体验**：节目列表/搜索是 C 端高频读，需要高效检索能力。

### 原来的方案有什么问题
- **无入口防护**：请求直接打到后端，开票高峰时后端直接被压垮；
- **裸接口**：登录/下单接口没有频率控制，脚本可以无限刷；
- **全量发布**：每次上线都是全量切换，灰度发布、快速回滚缺失；
- **DB 检索慢**：节目搜索走 MySQL `LIKE`，数据量大后检索慢、影响主库。

### 为什么需要重新设计
在**网关层**做统一防护与扩展能力：粗粒度熔断（信号量）→ 细粒度接口限流（Lua 滑动窗口）→ 防刷验证码（Lua 计数）→ 灰度发布（负载均衡过滤）→ ES 检索（异步索引 + 降级）。

> 一句话背景叙述（面试开场用）：
> "开票瞬间大量请求涌入网关，脚本刷票、恶意攻击也集中在这时候。我们在入口层做了四件事：网关信号量粗粒度熔断 + Lua 滑动窗口接口限流兜住流量；验证码防刷识别异常请求；灰度发布让新版本小流量验证、出问题快速回滚；ES 支撑节目检索，异步同步索引、DB 降级兜底。"

## 2. 整体架构

### 入口防护分层（网关层，从外到内）
```
请求进入 Gateway
  → ① 信号量熔断（RateLimiter）粗粒度 fail-fast：整体流量超水位直接拒绝
  → ② 身份/请求校验（RequestValidationFilter）
  → ③ 接口级限流（ApiRestrictService + apiLimit.lua 滑动窗口）：按接口/规则限流
  → ④ 灰度负载均衡（GrayReactiveLoadBalancer）：按请求头 gray 标记过滤实例
  → 转发到下游服务

下游服务（user-service）
  → 验证码防刷（UserCaptchaService + checkNeedCaptcha.lua）：
      登录/注册等接口按操作频率决定是否弹验证码

下游服务（program-service）
  → ES 检索（programEs.search / selectPage）：
      节目搜索/列表走 ES，无结果/异常降级 DB（dbSelectPage）
```

### 核心组件关系
```
网关限流：
  RateLimiter（Semaphore 粗粒度） → ApiRestrictService（Lua 滑动窗口细粒度）
验证码防刷：
  RequestCounter（JVM 本地，每秒计数）→ UserCaptchaService（Lua Redis 计数）
灰度发布：
  GrayReactiveLoadBalancer（请求头 gray + 实例元数据匹配）
ES 检索：
  ProgramElasticsearchInitData（启动全量同步）→ programEs.search/selectPage → dbSelectPage 降级
```

## 3. 核心技术方案拆解

---

### 技术点 A：网关信号量熔断（RateLimiter）—— 为什么用 Semaphore 而不是计数器

**是什么**：`RateLimiter` 基于 `Semaphore(maxPermitsPerSecond)`，在网关 filter 最外层做粗粒度熔断：`tryAcquire(1, 1s)` 获取许可证，超时直接抛 `OPERATION_IS_TOO_FREQUENT`。

**为什么用信号量（对比计数器/令牌桶）**：
- **信号量 = 并发水位控制**：限制的是"同一时刻有多少请求在途"，而不是"每秒多少个请求"；
- 网关本身不耗 CPU 做业务，瓶颈在并发在途数；Semaphore 语义直接对应"同时能放进去多少请求"；
- `tryAcquire(超时1s)` 快速失败，**不排队等待**，高水位时直接拒绝，保护下游；
- 简单可靠，是"粗粒度兜底"，细粒度交给 Lua 限流。

**为什么放在 filter 最外层**：优先级高于身份验证和业务限流——整体超载时先保命，不浪费资源做后续校验。

**风险**：信号量是 JVM 本地状态，**多实例各计各的**，不全局精确。
**优化**：它只是"兜底水位"，精确限流由 Redis Lua 滑动窗口做（全局一致），两者职责互补。

---

### 技术点 B：接口级限流 —— apiLimit.lua 滑动窗口怎么实现

**是什么**：`ApiRestrictService` + `apiLimit.lua` 对接口做**细粒度限流**，Lua 脚本实现滑动窗口计数。

**为什么用 Lua 滑动窗口（对比固定窗口）**：
- **固定窗口的缺陷**：按"每秒一个窗口"计数，窗口边界处会瞬间翻倍（如 23:59:59.999 和 00:00:00.000 各打满一次），漏掉突发；
- **滑动窗口更平滑**：按规则时间窗口（statTime）计数，配合限流标记（ruleLimitKey）的 effectiveTime 生效期，实现"超阈值后持续拦截一段时间"；
- Lua 原子执行，多实例全局一致（Redis 单 key 计数）。

**怎么做**（代码锚点 `apiLimit.lua`）：
- `incrby` 计数，首次 `expire` 设统计窗口；
- 超过阈值（threshold）→ `set ruleLimitKey` + `expire effectiveTime`（限流生效期）→ 返回触发；
- 限流标记存在期间，后续请求直接触发；
- 记录触发到 zset（`zSetRuleStatKey`）用于统计/通知（首次触发 `trigger_call_Stat=1`）。

**支持多级规则**：`ruleType/ruleKey/threshold/effectiveTime/statTime` 由配置驱动，不同接口不同阈值。

**风险**：Lua 脚本若配置错误（如 effectiveTime 过长）会长时间误拦。
**优化**：规则配置集中管理 + 限流统计可观测（zset 记录触发）。

### 技术点 C：验证码防刷 —— 为什么在"用户服务"而不是网关

**是什么**：`UserCaptchaService` + `checkNeedCaptcha.lua` 根据用户操作频率决定是否弹出滑块验证码。登录/注册等接口调用 `checkNeedCaptcha()`，超阈值返回"需要验证码"。

**为什么在 user-service 而不是网关**：
- 验证码是**业务动作**（登录/注册），需要业务上下文（用户、接口、设备）；
- 网关只做无状态的路由/限流；验证码状态要落 Redis，业务服务操作更自然；
- 与业务规则（阈值、始终验证开关）耦合，放业务侧可配置。

**怎么做**（代码锚点 `checkNeedCaptcha.lua` + `RequestCounter`）：
- **Lua 计数（Redis）**：`checkNeedCaptcha.lua` 用 Redis 计数 + 1 秒时间窗口重置，连续失败超过 `verify_captcha_threshold`（默认 10）→ 设 `verify_captcha_id=yes`（TTL 60s）→ 返回需要验证码；
- **始终验证开关**：`always_verify_captcha=1` 时恒弹验证码；
- **本地计数兜底**：`RequestCounter`（JVM 本地 AtomicInteger，每秒阈值默认 1000）用于高频场景本地快速判断，超阈值返回 true 触发验证码，避免每次判断都打 Redis；
- 注册链路：`UserRegisterVerifyCaptcha` 校验验证码是否匹配（`captchaHandle.verification`）。

**为什么计数放 Redis（Lua）**：多实例共享计数，全局一致；Lua 原子避免并发漏计。

**风险**：Redis 计数打满高频接口会额外消耗；本地 RequestCounter 各实例独立。
**优化**：两级——本地快速判断 + Redis 精确计数；阈值可配置。

### 技术点 D：灰度发布 —— 网关怎么按请求路由到灰度实例

**是什么**：`GrayReactiveLoadBalancer` 实现 Spring Cloud LoadBalancer 的 `ReactorServiceInstanceLoadBalancer`，按请求头 `gray` 标记过滤候选实例。

**为什么需要灰度**：
- **全量发布风险高**：新版本直接切全量流量，出问题影响所有用户，回滚也难；
- **小流量验证**：先让灰度实例接收部分请求，验证稳定性后再全量；
- **定向灰度**：可按请求头让特定用户/渠道走灰度（如内部测试号）。

**怎么做**（代码锚点 `GrayReactiveLoadBalancer.choose/filterByGray`）：
- **读取请求上下文**：`getGrayFromRequest` 从 `RequestDataContext` 拿请求头 `gray`（从请求上下文而非 ThreadLocal 读，避免网关响应式链路的线程切换问题）；
- **过滤实例**：`filterByGray` 按实例元数据（`instance.getMetadata().get(gray)`）匹配——请求带 gray 标记 → 只选元数据 gray=true 的实例；否则只选 gray=false 的实例；
- **空结果降级**：过滤后无实例（如没有灰度实例）→ **回退到全部实例**，避免流量中断；
- **轮询选择**：过滤后按 `position % size` 轮询选一个实例。

**风险**：若请求头未透传或元数据缺失，可能全部流量走灰度/非灰度，失去分流意义。
**优化**：请求头统一透传 + 实例元数据标准化 + 空结果降级兜底。

### 技术点 E：ES 检索 —— 为什么用 ES、怎么保证和 DB 一致

**是什么**：节目搜索/列表/推荐走 Elasticsearch（`programEs.search / selectPage`），启动时 `ProgramElasticsearchInitData` 把 DB 节目数据全量同步到 ES 索引。

**为什么用 ES（对比 MySQL LIKE）**：
- **检索性能**：节目名/描述模糊搜索，MySQL `LIKE '%xx%'` 无法走索引、数据量大后慢，且拖累主库；
- **分词/相关性**：ES 支持分词、全文检索、相关性排序，搜索体验好；
- **查询隔离**：C 端高频搜索从主库剥离，减少对订单/交易库的压力。

**怎么做**：
- **全量初始化**：启动时 `ProgramElasticsearchInitData`（executeOrder=3）把 DB 节目数据异步全量写入 ES 索引；
- **查询**：`search(programSearchDto)` → ES 查询 → 组装 VO；
- **降级**：ES 无结果或异常 → `dbSelectPage / dbSelectHomeList` 走 DB 兜底；
- **数据变更同步**：节目下架 `programEs.deleteByProgramId`，节目更新同步 ES（衔接多级缓存失效链路）。

**风险**：ES 与 DB 短暂不一致（ES 索引滞后）；ES 宕机时查询能力退化。
**优化**：ES 为主、DB 降级兜底；索引更新走业务事件驱动 + 全量重同步机制。

---

### 技术点 F：整个入口层怎么协同（链路视角）

**是什么**：四层防护不是孤立的，是一个从外到内、从粗到细的漏斗。

**协同逻辑**：
```
① 信号量熔断（全局水位）→ 挡住"超过系统承载"的洪峰
② 接口限流（Lua 滑动窗口）→ 按接口/规则精确限流
③ 验证码防刷（登录/下单）→ 挡脚本和恶意操作
④ 灰度发布 → 发布期小流量验证
⑤ ES → 检索能力提升 + 降级
```

**为什么这样分层**：
- 每层职责单一、可独立开关；
- 粗粒度在前（快、无状态），细粒度在后（精确、有状态）；
- 任一层故障都不致命：信号量挡不住还有接口限流，限流误拦还有验证码正常放行，ES 挂了还有 DB。

**风险**：层数多，配置分散，需要统一管理。
**优化**：规则集中配置（接口维度 threshold/effectiveTime）、监控各层触发率。

## 4. 重点准备追问链（三层连问）

### 追问链 1：从"限流怎么做"出发
- **第一层**：网关怎么限流？
  - 答：两层——信号量粗粒度熔断 + Lua 滑动窗口接口限流。
- **第二层**：为什么用信号量？
  - 答：控制并发在途数，快速失败保命，粗粒度兜底。
- **第三层**：信号量和接口限流有什么不同？
  - 答：信号量是 JVM 本地并发水位，接口限流是 Redis 全局精确计数；互补。

### 追问链 2：从"滑动窗口 vs 固定窗口"出发
- **第一层**：为什么用滑动窗口？
  - 答：固定窗口在窗口边界会瞬间翻倍，漏掉突发流量。
- **第二层**：怎么实现？
  - 答：Lua 脚本 Redis 计数 + 超阈值设限流标记（effectiveTime 生效期）。
- **第三层**：限流标记存多久？
  - 答：effectiveTime 配置控制；标记存在期间持续拦截，过期自动恢复。

### 追问链 3：从"验证码防刷"出发
- **第一层**：怎么判断要不要弹验证码？
  - 答：按用户操作频率——1 秒内失败超过阈值就要求验证码。
- **第二层**：计数放哪？
  - 答：Lua Redis 计数（全局一致）+ JVM 本地 RequestCounter（快速判断）。
- **第三层**：验证码服务放哪、为什么？
  - 答：user-service，因为是业务动作需要业务上下文，网关只做无状态路由。

### 追问链 4：从"灰度发布"出发
- **第一层**：灰度怎么做？
  - 答：网关负载均衡器按请求头 gray 标记过滤实例。
- **第二层**：灰度实例怎么标识？
  - 答：实例注册元数据 gray=true/false，按请求头匹配。
- **第三层**：没有灰度实例会怎样？
  - 答：过滤结果为空时回退到全部实例，避免流量中断。

### 追问链 5：从"ES 检索"出发
- **第一层**：节目搜索为什么用 ES？
  - 答：模糊搜索 MySQL 走不了索引、慢，且拖累主库。
- **第二层**：ES 数据从哪来？
  - 答：启动时全量同步 DB 数据到索引，变更时事件驱动更新。
- **第三层**：ES 挂了怎么办？
  - 答：查询无结果/异常降级到 DB 兜底（dbSelectPage）。
