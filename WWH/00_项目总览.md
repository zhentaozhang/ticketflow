# 主题 00：项目总览 —— 面试深挖分析

---

## 1. 项目定位（一句话）

**高并发在线票务交易系统**（抢票/售票场景），面向演唱会、体育赛事等**开票瞬间流量暴增**的业务，核心目标：**不超卖、扛高峰、稳定可用**。

> 面试开场叙述：
> "我负责一个高并发在线票务交易系统，核心场景是开票瞬间几十万用户同时抢票。整个项目围绕三件事设计：库存不能超卖、高峰流量要扛得住、出问题能快速发现和恢复。技术上的四大核心工作是订单分库分表、统一分布式锁、多级缓存、Redis+Kafka 异步下单链路，另外在入口层做了限流、防刷、灰度和搜索能力。"

## 2. 整体架构 —— 微服务拆分

### 服务列表（`ticketflow-server/`，Spring Cloud 微服务）

| 服务 | 职责 | 关键代码 |
|------|------|---------|
| **gateway-service** | 网关：信号量熔断、Lua 滑动窗口限流、请求/响应校验、灰度负载均衡 | `RateLimiter`、`ApiRestrictService`、`RequestValidationFilter`、`GrayReactiveLoadBalancer` |
| **user-service** | 用户：注册/登录/Token、购票人管理、验证码防刷 | `UserService`、`UserCaptchaService`、`checkNeedCaptcha.lua` |
| **program-service** | 节目：节目详情/列表/搜索（ES）、票档、座位、下单入口（Lua 扣库存）、缓存失效广播 | `ProgramService`、`ProgramOrderService`、`ProgramOrderV5Strategy`、`LocalCacheProgram` |
| **order-service** | 订单：建单（Kafka 消费）、取消、支付、订单列表、投影任务 | `OrderService`、`CreateOrderConsumer`、`DelayOrderCancelConsumer`、`OrderDbProjectionTask` |
| **pay-service** | 支付：支付宝/微信、支付单、退款单 | `PayService`、`PayBillService`、`RefundBillService` |
| **base-data-service** | 基础数据：地区、渠道 | `AreaController`、`ChannelDataController` |
| **customize-service** | 定制能力：消息记录、规则、对账（消息对账补偿） | `MessageRecordService`、`ReconciliationTask`、`DelayOrderCancelExceptionMessageHandler` |
| **migrate-service** | 数据迁移：分片迁移（Hint 强制路由）、限速/预演/幂等 | `ShardingMigrationService`、`TableOrderHintShardingAlgorithm` |
| **admin-service** | 后台管理：监控 | `monitor` |

### 服务间通信
- **同步 RPC**：Feign（如 program 调 order 建单接口、order 调 pay 支付）；
- **异步消息**：Kafka（建单 `create_order`、网关数据上报）+ Redis Stream（本地缓存失效广播）+ 自研延迟队列（超时取消/延迟操作）；
- **网关负载均衡**：灰度 `GrayReactiveLoadBalancer`。

## 3. 框架沉淀 —— 可复用能力（这是项目的工程化亮点）

项目把高频通用能力抽成了独立模块（`ticketflow-*-framework`），面试讲"工程化能力"时从这里引。

| 框架 | 职责 | 关联主题 |
|------|------|---------|
| **id-generator-framework** | 分布式 ID：雪花（主键/订单号）+ 基因嵌入；时钟回拨处理、序列随机起点；百度 UidGenerator 缓存批量生成 | 01 分库分表 |
| **redis-tool-framework** | Redis 组件：`RedisCache` 封装（Cache-Aside、Hash、批量）、`RedisKeyBuild`（环境隔离前缀）、**Redis Stream 广播组件**（`RedisStreamHandler`/`PushHandler`/`AutoConfig`） | 03 多级缓存 |
| **redisson-framework** | Redisson 生态封装：`service-lock`（4 种锁 + 注解 + 切面）、`repeat-execute-limit`（幂等）、`bloom-filter`（防穿透）、`delay-queue`（延迟队列 + 分区） | 02 分布式锁 / 04 异步下单 |
| **elasticsearch-framework** | ES 客户端封装（`BusinessEsHandle`） | 05 入口防护 |
| **captcha-manage-framework** | 滑块验证码组件 | 05 入口防护 |
| **spring-cloud-framework** | Spring Cloud 通用：`service-common`（分片算法/数据基类/分页/异常）、`service-initialize`（启动初始化框架）、灰度过渡框架 | 01/全局 |
| **thread-pool-framework** | 业务线程池（`BusinessThreadPool`）、拒绝策略 | 04 异步下单 |
| **common** | 公共：常量/异常/JWT/环境隔离/JSON 日志（log4j） | 全局 |

> 面试话术：
> "项目不只是业务代码，我们把高频能力沉淀成了框架模块：ID 生成、Redis 组件、Redisson 生态（锁/幂等/布隆/延迟队列）、ES、验证码、线程池，都是独立模块。一是避免各服务重复造轮子，二是这些框架本身就是工程能力的体现。比如 Redis 组件里封装了 Redis Stream 的消费组自动配置，延迟队列里做了隔离分区。"

## 4. 核心业务链路（四大主题串起来）

### 链路 1：用户下单（核心主链路）
```
用户点击下单（program-service）
  → 网关：信号量熔断 → Lua 滑动窗口限流（05 入口防护）
  → user-service：登录态/验证码防刷（05）
  → program-service：
      composite 校验链（登录/限购/购票人/布隆过滤器）
      → 本地余票预判（售罄短路，03 多级缓存）
      → Lua 一次 EVAL：幂等 SETNX + 校验余票/座位/价格 + 锁座 + 扣余票 + 写流水（04 异步下单）
      → 预生成订单号（含 userId 基因，01 分库分表）
      → 发 Kafka 建单消息 + 投递延迟取消消息
  → order-service：CreateOrderConsumer 消费 → createMq 落库（订单/购票人/记录/订单节目）
  → 用户支付 → pay-service → 支付回调 → 座位 SOLD + DB 库存确认
  → 超时未支付 → 延迟队列 → cancel → 座位解锁 + 库存回补
```
链路贯穿主题：**01（订单号基因）+ 02（状态流转锁）+ 03（缓存失效广播）+ 04（异步+延迟）+ 05（入口防护）**。

### 链路 2：数据查询
```
节目列表/搜索 → ES（05）→ 无结果降级 DB
节目详情 → 布隆过滤器 → Caffeine 本地 → Redis → double-checked locking → DB（03）
订单列表 → 按 user_id 精准路由单分片（01）
订单详情 → 按 order_number 精准路由（01）
```

### 链路 3：数据一致性与对账（兜底）
```
扣库存（Redis Lua，权威）→ Kafka 建单 → DB 落库
  → 不一致兜底：消息消费记录（customize-service）+ ReconciliationTask 对账 + 丢弃订单（04）
缓存一致性：Redis Stream 广播失效 → 各实例本地缓存删除（03）
```

## 6. 主题之间的关系（01~05 怎么串）

```
          ┌─────────────── 入口层（05）──────────────┐
          │  限流 / 防刷 / 灰度 / ES                  │
          └────────────────┬────────────────────────┘
                           ▼
    ┌─────────── 业务核心层 ───────────┐
    │  下单链路（04）                  │
    │    Lua 扣库存 → Kafka → 延迟取消   │
    │    │                              │
    │    ├─ 依赖 Redis 缓存（03）        │
    │    ├─ 依赖分布式锁（02）           │
    │    └─ 订单落库走分片（01）          │
    └───────────────────────────────────┘
```

- **01 分库分表**：订单数据的存储底座，基因法让订单号自描述路由；
- **02 分布式锁**：状态流转（取消/支付）并发互斥的框架底座；
- **03 多级缓存**：读路径的性能底座 + 一致性（Stream 广播）；
- **04 异步下单**：写路径的吞吐底座（Lua 原子 + Kafka 削峰 + 延迟兜底）；
- **05 入口防护**：所有能力的第一道防线。

> 面试总结话术：
> "这四块不是孤立的：订单号基因（01）决定订单落哪个库表，多级缓存（03）扛读、异步下单（04）扛写、分布式锁（02）保证状态流转不乱，入口层（05）先把异常流量挡在外面。整个链路用'幂等 + 状态机 + 对账'收敛到最终一致。"
