# 主题一：ShardingSphere 基因法分片 —— 面试深挖分析

> 基于"业务问题 → 技术方案 → 设计原因 → 实现方式 → 遇到问题 → 优化方案 → 极端情况处理"链路。
> 每个技术点按「是什么 / 为什么 / 怎么办」三层组织，代码锚点均经 codegraph 核实。

---

## 1. 项目背景

### 业务场景
这是一个在线售票（抢票）系统。订单是核心写入数据，具备三个特征：
- **写入高频且集中**：开票瞬间大量用户同时下单，订单表写入压力瞬间爆发；
- **用户视角访问**：用户高频操作是"查我的订单列表（user_id）"和"查单个订单详情（order_number）"；
- **数据持续增长**：单表行数持续膨胀，索引深度增大，写入和查询性能都会退化。

### 原来的方案有什么问题
单库单表下：
- **写入瓶颈**：订单表成为单点，开票高峰的写吞吐受限于单表（行锁、索引维护、redo log）；
- **查询退化**：行数过亿后 B+ 树层级加深，即使命中索引，随机 IO 变多，延迟劣化；
- **无法水平扩展**：单实例 MySQL 能力有物理上限，加 CPU/内存收益递减。

### 为什么需要重新设计
必须把订单数据**水平拆分**到多个库、多张表，把压力分摊到更多物理节点。但水平拆分不是"拆了就行"，它引入两个新的核心难题——**路由**与**查询适配**，而这两个难题正是基因法分片要解决的。

> 一句话背景叙述（面试开场用）：
> "订单表数据量大、开票写入集中，单表扛不住。我们做了水平分库分表（2 库 8 表）。但拆完之后最大的问题变成了：按 order_number 查详情、按 user_id 查列表，这两个维度怎么都能精确路由到同一分片？如果路由不准，就会退化成全分片广播——也就是读扩散。我们最终用基因法分片解决了这个问题。"

## 2. 整体架构

### 分片拓扑（来自 `shardingsphere-order-local.yaml`）
```
数据源（库）: ds_0 / ds_1 （2 个库，ticketflow_order_0 / ticketflow_order_1）

表分片：
  d_order                      2 库 × 8 表
  d_order_ticket_user          2 库 × 8 表
  d_order_ticket_user_record   2 库 × 8 表
  d_order_program              2 库 × 2 表

分片列：
  d_order                      复合分片列 order_number + user_id
  d_order_ticket_user 等关联表  分片列 order_number

绑定关系（bindingTables）：
  [d_order, d_order_ticket_user, d_order_ticket_user_record]  绑定表
  [d_order_program]                                           单独一组

广播表（broadcastTables）：undo_log
```

### 关键数据流
```
下单（program-service）
  buildCreateOrderParam → uidGenerator.getOrderNumber(userId)
     ↑ 订单号 = [时间戳][数据中心][机器][序列号<<6][userId后6位]
     ↑ 基因在订单号生成这一刻就被"写入"
  → 订单号随 Kafka 消息进入 order-service
  → order-service 落库，ShardingSphere 按 order_number（含基因）路由
```

### 两个维度的路由如何落进同一分片（架构核心）
- **按 user_id 查**：`user_id` 本身直接作为分片键 → 取它低 6 位的基因算索引；
- **按 order_number 查**：`order_number` 低 6 位与 `user_id` 低 6 位**相同**（生成时写入）→ 同一套位运算算出的索引一致。
- 结果：**两个查询维度都能精确命中同一物理分片**，互不依赖映射表。

> 架构叙述锚点：
> "分片键是双维度——d_order 上同时配置了 order_number 和 user_id 两个分片列。它们能路由到同一分片，不是靠映射表，而是靠订单号生成时把 userId 后 6 位直接嵌进了订单号。这是基因法的本质。"

## 3. 核心技术方案拆解

### 技术点 A：为什么选 ShardingSphere（而不是 MyCat / 自研）

**是什么**：用 ShardingSphere 作为分库分表中间件，Java 接入，配置驱动。

**为什么**：
- **内嵌式**（Sharding-JDBC）：在应用内做 SQL 解析 + 路由 + 改写，无独立代理节点，链路短、无额外网络跳转，性能损耗小；
- **支持自定义分片算法**：这是选择它的**决定性理由**——基因法需要自定义 `ComplexKeysShardingAlgorithm`，ShardingSphere 的 SPI 扩展点正好支持；
- Java 生态、和 MyBatis-Plus 配合成熟。

**为什么不用其他方案**：
- **MyCat**：代理模式，多一层网络转发；自定义分片算法扩展不如 ShardingSphere 的 SPI 灵活；
- **自研**：SQL 解析、路由、改写、分布式事务都要自己实现，工程量大且易错。

**风险**：SQL 兼容性（不支持的 SQL 会报错）、规则配置复杂。
**优化**：业务 SQL 尽量标准化，复杂 SQL 拆解或走路由；规则集中在配置文件中统一管理。

---

### 技术点 B：分片键为什么选"用户维度 + 双分片键"

**是什么**：d_order 的分片列为 `order_number` 和 `user_id`（复合），其余订单关联表只用 `order_number`。

**为什么选用户维度**：
- 订单的访问模式**天然按用户聚合**：查订单列表是 user_id，查详情是 order_number；
- 用户维度分片后，**同一个用户的所有订单落在同一分片**，用户维度的查询都不需要跨库；
- 对比：如果按节目（program_id）分片，开票瞬间某个热门节目就是热点写，全打在单片上，**人为制造热点**，且用户跨多个节目的订单会散落各处，查"我的订单"必跨库。所以节目维度不可取。

**为什么双分片键（为什么不是单一 order_number）**：
- 如果只按 `order_number` 分片：用户查订单列表 `WHERE user_id = ?` 时**没有 order_number 作为分片键**，ShardingSphere 无法路由，只能**广播到全部分片**再合并——这就是读扩散，代价随分片数线性放大；
- 双分片键 + 基因法，让 `user_id` 和 `order_number` 都能作为路由入口，且路由结果一致。

**风险**：分片键是**不可变约束**——一旦数据入库，用户无法改分片键，否则数据路由不到原位置。
**优化**：分片键在设计初期就定死，业务上禁止修改订单的 user_id / order_number。

### 技术点 C：基因法核心设计 —— 订单号嵌入 userId 低 6 位（本主题最深点）

**是什么**：`SnowflakeIdGenerator.getOrderNumber(userId)` 生成的订单号，结构为：
```
[时间戳] [datacenterId] [workerId] [sequence << 6] [userId & 0b111111]
                                                   └─ 低 6 位是用户基因
```

**为什么**：
- 核心矛盾：需要**两个查询维度都能精确路由**，但数据库里 `user_id` 和 `order_number` 是两个独立字段，它们本身没有数学关联；
- 基因法的解决思路：**在数据生成那一刻，把 user_id 的部分信息（低 6 位）"拷贝"进 order_number**，人为建立两者的关联；
- 这样计算分片索引时，无论拿 order_number 还是 user_id，取低 6 位得到的是**同一个值** → 分片索引一致 → 双维度精确路由。

**怎么做**（代码锚点 `SnowflakeIdGenerator.getOrderNumber`）：
```java
long fixedGeneLength = 6L;
long geneMask = (1L << 6) - 1;          // 0b111111
long userGene = userId & geneMask;      // 取 userId 后 6 位
return ((timestamp - BASIS_TIME) << timestampLeftShift)
        | (datacenterId << datacenterIdShift)
        | (workerId << workerIdShift)
        | (sequence << fixedGeneLength)
        | userGene;                     // 嵌入基因
```

**为什么是 6 位**：
- 6 位可表示 2⁶ = 64 种组合，覆盖最大 8 库 × 8 表（8 库×8 表 = 64 种分片组合，正好用满 6 位）；
- 当前配置是 2 库 8 表（库需 1 位、表需 3 位，共 4 位），**预留了 2 位**，未来扩容到 8 库 8 表无需改生成逻辑，只改分片配置。

**风险**：基因来自 userId 低位，若 userId 分布不均会传导到分片分布。
**优化**：userId 用雪花/UidGenerator 自增生成，低位天然近似均匀；低流量冷启动阶段额外用"随机序列起点"缓解热点（见技术点 E）。

### 技术点 D：位运算分片 —— 为什么要求 2 的幂、库表索引怎么叠加

**是什么**：`ShardingGeneUtils` 统一封装分片位运算：
```java
tableIndex    = (tableCount - 1) & shardingKey;                  // 低 N 位 = 表基因
databaseIndex = (dbCount - 1) & (shardingKey >> tableGeneLength); // 跳过表基因位后取 M 位 = 库基因
```

**为什么要求分片数必须是 2 的幂**：
- `(count - 1) & value` 只有在 count 是 2 的幂时，才**等价于 `value % count`** 且分布完全均匀；
- 若 count 不是 2 的幂（如 3、5），位与运算会丢位、产生**取模偏差**，某些分片永远命中不了或过载；
- 代码用 `checkPowerOfTwo` 在启动时 fail-fast 校验，配置错误直接抛异常，**避免静默错误路由**。

**为什么库索引要"跳过表基因位"再取高位**：
- 基因位要同时服务"表"和"库"两个维度，必须**分段复用**：
  - 低 N 位（N = log2 表数）→ 表基因；
  - 紧接着的 M 位（M = log2 库数）→ 库基因；
- 如果库表取的是同一段位，会出现"同一个值算出的表索引和库索引互相矛盾"或"两段基因重叠被覆盖"的问题；
- 示例（配置是 2 库 8 表，表基因 3 位）：表索引取 bit0-2，库索引取 bit3。同一基因同时定位到 1 张表和 1 个库，组合成唯一物理分片。

**怎么做**（代码锚点）：
- `tableGeneLength = Long.numberOfTrailingZeros(tableCount)`（log2，位运算代替浮点，避免精度误差）；
- `tableIndex = (tableCount - 1) & value`；
- `databaseIndex = (dbCount - 1) & (value >> tableGeneLength)`。

**风险**：分片数配置错误（非 2 的幂）会静默错路由。
**优化**：启动校验 + 配置中心统一管理分片数。

### 技术点 E：雪花算法改造 —— 为什么序列号要 6 位、时钟回拨、随机起点

**是什么**：订单号在标准雪花算法上做了定制，独立于主键 ID 的生成逻辑（主键 ID 用标准 12 位序列，订单号用 6 位序列）。

**为什么序列号必须用 6 位（而不是标准 12 位）**：
- 标准雪花序列是 12 位，`sequence << 12` 会占掉太多位；
- 基因法订单号结构是 `[时间戳][datacenter][worker][sequence<<6][基因6位]`——**序列号必须左移 6 位，正好空出低 6 位给基因**；
- 若沿用 12 位序列，左移 12 位会**覆盖掉 workerId / datacenterId 位段**，破坏订单号唯一性；
- 代价是每毫秒订单号上限从 4096 降到 64（6 位），但对订单场景足够。

**时钟回拨怎么处理**（`getBase`）：
- 回拨 ≤ 5ms：`wait(offset << 1)` 等待回拨时间的两倍后重试；
- 回拨 > 5ms：直接抛异常拒绝生成，**避免生成重复订单号**。

**为什么新毫秒序列号要从 [1,64) 随机起点**（`initialSequence`）：
- 低流量冷启动时，若每个毫秒序列号都从 0 起步，那么"低 6 位基因"在一天里只会覆盖很少几种组合 → 分片分布极度不均匀（全打到少数分片）；
- 改为随机起点后，即使低流量，也能让基因位覆盖到更全的组合，**缓解冷启动阶段的分布热点**。

**风险**：单毫秒 64 个上限，极端突发可能瞬间打满。
**优化**：打满时 `tilNextMillis` 自旋等待下一毫秒（代码已处理）。

### 技术点 F：复合分片算法 —— 多分片列如何协同 + fail-fast 防呆

**是什么**：`DatabaseOrderComplexGeneArithmetic` / `TableOrderComplexGeneArithmetic` 实现 `ComplexKeysShardingAlgorithm<Long>`，在 `doSharding` 里解析分片列并路由。

**为什么选复合算法而不是简单取模算法**：
- 需要同时识别 `order_number`、`user_id`、`id`、`program_id`、`out_order_no` 等多个分片列（不同业务场景查询入口不同）；
- 标准 `MOD`/`HASH_MOD` 算法只针对单一列，无法处理"双分片键、多查询入口"的场景。

**怎么做**：
- `doSharding` 从 `columnNameAndShardingValuesMap` 解析分片列的值，优先级：`order_number` → `user_id` → `id` → `program_id` → `out_order_no`；
- 用取到的值调 `ShardingGeneUtils` 计算库/表索引；
- **fail-fast 防呆**：当 `order_number` 和 `user_id` **同时**出现在查询条件时，分别计算两者索引并比对，不一致直接抛 `IllegalArgumentException`——防止基因位定义漂移导致静默错路由；
- 库名匹配用 `equals("ds_" + index)` 而非 contains，避免 `ds_1`/`ds_10` 前缀误匹配。

**风险**：`program_id`、`out_order_no` 这些"非基因分片键"怎么路由？
- 设计上 `program_id` 与 `id` 同值域、`out_order_no` 就是订单号字符串，与 order_number 等价——**它们不是靠基因路由，而是靠"与某个基因分片键值相同"来复用同一套路由**。这一块面试官很可能追问，要能讲清楚。

**优化**：命中时通过 `ShardingMetrics.recordDatabaseHit(index)` 记录路由分布，供热点监控（见技术点 H）。

### 技术点 G：数据迁移 —— Hint 强制路由绕过分片算法

**是什么**：`TableOrderHintShardingAlgorithm` / `DatabaseOrderHintShardingAlgorithm`，配合 `HintManager.addTableShardingValue()/addDatabaseShardingValue()` 强制指定物理库表。

**为什么需要**：
- 分库分表上线前/扩容时，要把历史数据从老表/老库**搬迁到正确的分片**；
- 搬迁过程是"按目标物理表逐张搬"，如果继续走分片算法，ShardingSphere 会**重新计算路由**，可能把数据导到错误的分片；
- Hint 强制路由让 SQL **无视分片算法、直达指定物理表**，搬迁工具才能精确控制每批数据的落点。

**怎么做**：在 ShardingSphere 的 Hint 上下文中指定目标物理表名（如 `d_order_0`），算法直接返回该物理表。

**风险**：Hint 是"绕过规则"的能力，用错会破坏路由一致性。
**优化**：只在迁移服务（`migrate-service`）中使用，业务服务不开放。

---

### 技术点 H：分片热点监控

**是什么**：`ShardingMetrics` 记录每次路由命中的分片索引 + `ShardingRoutingMonitorTask` 定时输出路由分布快照。

**为什么**：分片设计再好，实际流量分布仍需观测——某个 userId 段的用户异常活跃，可能把某个分片打热；没有监控就发现不了。

**怎么做**：路由算法命中库时 `recordDatabaseHit(index)` 计数，定时任务把各分片命中数打印成快照日志，人工或告警判断是否出现热点。

**风险**：监控数据可能被低估（只统计了显式带分片键的查询）。
**优化**：配合 Redis/DB 指标、业务埋点多维观测。

---

### 技术点 I：绑定表 / 广播表

**是什么**：
- `bindingTables`: `d_order, d_order_ticket_user, d_order_ticket_user_record` 绑定；`d_order_program` 单独一组；
- `broadcastTables`: `undo_log`。

**为什么**：
- **绑定表**：这 3 张表按相同规则（同一库同一表后缀）分片，**关联查询（JOIN）时无需跨库/跨表**，能在单分片内完成，避免分布式 JOIN。订单关联表都用 order_number 分片，天然和订单同库同表；
- **广播表**：`undo_log` 是分布式事务日志表，每个库都要有完整一份，广播保证各库一致。

**风险**：绑定表必须保证分片规则完全一致，否则 JOIN 会退化。
**优化**：配置集中管理，分片规则变更同步评估关联表。

---

### 技术点 J：分片后的分布式事务（怎么回答）

**是什么**：分库分表后，一次业务可能跨多个库写入；项目里有 `undo_log` 广播表（典型 Seata AT 模式的落点）作为分布式事务基础设施。

**怎么回答（要诚实）**：
- **利用了"同用户同分片"减少跨库事务**：一个用户的一单，订单 + 关联表都在同一分片，**单库本地事务即可**，不需要分布式事务——这是基因法顺带带来的好处；
- 真正跨库/跨服务的操作（下单扣 Redis、异步落 DB、支付回调）**不追求强一致**，而是通过**异步 + 幂等 + 对账补偿**收敛为最终一致（这正好衔接"异步下单链路"主题）。

**风险**：如果未来有跨用户、跨节目的写操作，会重新引入分布式事务复杂度。
**优化**：业务建模上尽量保证"一次事务 = 一个分片"，从源头避免分布式事务。

## 4. 重点准备追问链（三层连问）

### 追问链 1：从"为什么订单号嵌 userId"出发
- **第一层**：为什么订单号要嵌 userId？
  - 答：为了支持 user_id 和 order_number 双维度精确路由，避免读扩散。
- **第二层**：为什么不直接用映射表 / 冗余一个 shard_id 字段？
  - 答：映射表本身是单点、多一次查询；冗余 shard_id 需要业务手动维护、易错。基因法让订单号**自描述路由信息**，零额外存储、零额外查询。
- **第三层**：那 userId 低 6 位会不会不够 / 分布不均？
  - 答：6 位覆盖 64 组合够当前 2 库 8 表；userId 自增低位近似均匀；低流量冷启动用随机序列起点缓解。

### 追问链 2：从"为什么是 2 的幂"出发
- **第一层**：为什么分片数要求 2 的幂？
  - 答：位与运算等价取模需要 2 的幂，否则有偏差。
- **第二层**：具体怎么偏？举 3 库的例子。
  - 答：(count-1) 不是全 1，某些高位被丢弃，部分分片永远选不中或过载，分布不均衡。
- **第三层**：如果未来要 3 库怎么办？
  - 答：要么扩容到 4 库（2 的幂），要么换哈希取模算法（性能稍差但支持任意库数）；基因法方案倾向保持 2 的幂。

### 追问链 3：从"跨库查询"出发
- **第一层**：基因法怎么避免跨库查询？
  - 答：用户维度 + 双分片键路由一致，用户订单都落同片。
- **第二层**：那管理后台按节目/按时间查订单呢？没有分片键。
  - 答：这种查询确实会全分片广播（读扩散），但它是低频后台操作，量小可接受；必要时走宽表/ES（项目里还有 Elasticsearch 框架）支撑检索。
- **第三层**：全分片广播最坏会怎样？
  - 答：N 个分片 = N 次查询 + 归并排序，延迟和资源随分片数线性放大，所以只留给低频查询。

## 5. 极端情况处理（怎么办层汇总）

| 场景 | 怎么办 |
|------|--------|
| 分片数配成非 2 的幂 | `checkPowerOfTwo` 启动即抛异常，fail-fast 不静默 |
| 时钟回拨 | ≤5ms 等待 2 倍偏移；>5ms 抛异常拒绝生成 |
| 单毫秒序列号打满 | `tilNextMillis` 自旋等到下一毫秒 |
| order_number 与 user_id 路由不一致 | 复合算法 fail-fast 抛异常，防止静默错路由 |
| 历史数据迁移 / 扩容 | Hint 强制路由，绕过分片算法精确指定物理表 |
| 分片热点 | `ShardingMetrics` + 定时快照监控，观测后调整/预热 |
| 无分片键查询（后台检索） | 全分片广播（低频可接受）或走 ES 宽表 |
| 跨分片事务 | 靠"同用户同分片"规避；必要时 Seata（undo_log 广播表已就位） |
| 扩容到更大规模 | 基因位预留 6 位，8库8表内只改配置不改生成逻辑 |
