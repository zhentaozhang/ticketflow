# 主题二：统一分布式锁框架 —— 面试深挖分析

> 基于"业务问题 → 技术方案 → 设计原因 → 实现方式 → 遇到问题 → 优化方案 → 极端情况处理"链路。
> 每个技术点按「是什么 / 为什么 / 怎么办」三层组织，代码锚点均经 codegraph 核实。

---

## 1. 项目背景

### 业务场景
抢票系统的核心写入是**订单状态流转**和**库存操作**，它们有一个共同特点：**同一份数据会被多个并发请求同时触碰**，例如：

- 用户点击"取消订单"和支付回调同时到达，订单状态该以谁为准？
- 下单、支付、取消、退单在同一订单上并发执行，状态机怎么不乱？
- Kafka 重复消费同一订单消息，会不会重复建单？
- 同一节目/票档的座位与余票操作，多实例并发下会不会写串？

### 原来的方案有什么问题
- **本地锁（synchronized / ReentrantLock）**：只对单个 JVM 进程有效。服务是**多实例部署**的，同一用户请求可能被负载均衡打到不同实例，本地锁跨实例完全失效；
- **数据库乐观锁/悲观锁**：依赖 DB 行锁，高并发下连接池和锁竞争成为瓶颈，且只保护 DB 内的数据，管不到"DB 外"的资源（如 Redis 扣减）；
- **裸写 SETNX**：容易踩坑（下面展开），且每个业务方各写一套，代码重复、容易错。

### 为什么需要重新设计
需要一个**统一、可靠、对业务零侵入**的分布式互斥能力：一套框架管住所有需要互斥的场景，业务方只需声明"我要锁什么"，不必关心锁怎么实现、怎么防死锁、怎么续期。

> 一句话背景叙述（面试开场用）：
> "订单状态流转（取消、支付）和库存操作存在多实例并发竞态，本地锁跨实例失效、裸写 SETNX 一堆坑。我们封装了一套基于 Redisson 的分布式锁框架：统一 4 种锁模型（可重入/公平/读/写），支持注解声明式和编程式两种用法，并且通过调整切面顺序实现了'加锁先于事务开启、释放晚于事务提交'，从框架层面解决锁与事务的时序竞态。"

## 2. 整体架构

### 框架分层（自下而上）
```
Redisson（底层）：原生锁能力（可重入/公平/读写锁 + watchdog 续期）

ServiceLocker 接口 + 4 个实现（RedissonReentrantLocker / FairLocker / ReadLocker / WriteLocker）
  └─ 统一契约：getLock / lock / tryLock / unlock

ManageLocker（启动时创建并缓存 4 种 locker）
ServiceLockFactory（策略模式：LockType → ServiceLocker）

两种使用入口：
  ① 注解式：@ServiceLock + ServiceLockAspect（@Order(-10)）
  ② 编程式：ServiceLockTool（execute / submit / getLock）

LockInfoHandle 体系：构造锁 key（含 SpEL 动态解析）
  ServiceLockInfoHandle → 前缀 "SERVICE_LOCK"
  RepeatExecuteLimitLockInfoHandle → 前缀 "REPEAT_EXECUTE_LIMIT"（与锁隔离）
```

### 锁 key 结构（代码锚点 `AbstractLockInfoHandle`）
```
{环境前缀}-{锁类型前缀}:{业务名}:{key值}
示例：default-SERVICE_LOCK:UPDATE_ORDER_STATUS_LOCK:1965791442215448582
说明：
  环境前缀（prefixDistinctionName）隔离多环境，防止本地/测试/生产锁互踩
  SpEL 动态解析 keys = {"#orderCancelDto.orderNumber"} → 取方法入参的订单号
  注解入口与编程式入口共用 getLockPrefixName()，保证同一业务名跨入口锁名一致、互斥生效
```

### 两个切面的执行顺序（架构核心，本主题最深点）
```
请求进入
  → RepeatExecuteLimitAspect（@Order(-11)）  幂等拦截，最外层
  → ServiceLockAspect（@Order(-10)）          加锁，在事务开启前
  → 事务拦截器（默认 Order = LOWEST_PRECEDENCE）事务开启
  → 业务方法
  → 事务提交
  → ServiceLockAspect 释放锁（在事务提交后）
  → RepeatExecuteLimitAspect 写入幂等标记（afterCommit，在事务提交后）
```

`@Order` 语义：数值越小优先级越高，处于代理链**外层**；`LOWEST_PRECEDENCE`（事务拦截器）在最内层。`@Around` 环绕语义下，**先进入者最后退出**——所以加锁发生在 `proceed()` 之前（早于事务开启），解锁在 `finally`（晚于事务提交）。

## 3. 核心技术方案拆解

### 技术点 A：为什么选 Redisson（而不是自研 SETNX / ZooKeeper / 数据库）

**是什么**：分布式锁底层基于 Redisson，在其原生锁能力上做框架封装。

**为什么选 Redisson**：
- **开箱即用、可靠**：可重入、公平锁、读写锁、watchdog 续期、Lua 原子释放，都是成熟实现；
- **避免重复造轮子**：自己实现这些要踩大量边界坑（见技术点 B）；
- **性能好**：纯 Redis 操作，比 ZooKeeper（ZAB 协议、重）和数据库锁快得多。

**为什么不用其他方案**：
- **ZooKeeper**：可靠但性能差，引入额外运维组件，抢票这种高 QPS 场景不划算；
- **数据库（select for update）**：DB 行锁 + 连接池在并发下是瓶颈，只能保护 DB 内资源；
- **自研 SETNX**：要自己处理过期、误删、可重入、主从切换等一系列问题，收益低风险高。

**风险**：Redis 主从切换时锁可能丢失（见技术点 H），无法做到绝对强一致。
**优化**：本项目锁保护的是"可重入的短临界区"操作，Redis 为主 + 业务侧幂等/对账兜底，接受极小概率失效。

---

### 技术点 B：裸写 SETNX 有哪些坑（为什么不能简单 SETNX + EXPIRE）

**是什么**：用 `SETNX lock_key value` 加锁、`EXPIRE` 设过期、`DEL` 释放，是自研分布式锁的"朴素写法"，存在多个经典坑。

**为什么这些坑会导致严重问题**：
- **加锁与过期不原子**：`SETNX` 和 `EXPIRE` 是两条命令，中间进程崩溃 → 锁**永久不死**（死锁）；
- **误删他人锁**：线程 A 锁超时释放，线程 B 拿到锁，A 执行完 `DEL` 把 B 的锁删了 → 两个线程同时"持有锁"；
- **不可重入**：同一线程嵌套加同一把锁直接失败或死锁；
- **主从切换丢锁**：锁写进主库未同步，主库宕机切从库，锁丢失 → 互斥失效。

**怎么做（本项目靠 Redisson 解决）**：
- 单命令原子加锁（`SET key value NX PX`）；释放用 Lua 脚本校验 value 再删，防止误删；
- 可重入用 hash 记录持有线程 + 重入计数；
- watchdog 自动续期防锁过期；
- Redisson 把这套都封装好了，我们不必重复实现。

**风险**：理解不到位会误以为"自己写个 SETNX 就行"，面试要能主动讲出这些坑。
**优化**：所以选择成熟框架，把精力放在业务上。

---

### 技术点 C：ServiceLocker 接口 + 4 种锁模型的设计

**是什么**：`ServiceLocker` 定义统一契约（getLock / lock / tryLock / unlock），4 个实现分别包装 Redisson 的 4 种锁。

**为什么统一接口**：
- **调用方只依赖抽象**：切面/工具类拿到的是 `ServiceLocker`，不关心具体锁实现；
- **策略模式 + 工厂分发**：`ServiceLockFactory.getLock(LockType)` 一行切换锁类型，业务方改一个枚举值即可换锁模型；
- **启动时缓存**：`ManageLocker` 启动时创建 4 种 locker 并缓存，避免每次加锁重复创建 Redisson 对象。

**4 种锁的语义与场景**：
- **Reentrant（可重入，默认）**：普通互斥。订单创建、支付回调与取消互斥（`OrderService.cancel` 用它）；
- **Fair（公平）**：按请求顺序排队，避免线程饥饿。**框架已实现，但业务未使用（预留能力）**——公平锁每次竞争走排队，吞吐低于普通可重入锁，抢票场景不需要饥饿保护，故未落地；
- **Read（读锁）**：可并发读、写互斥。`ProgramService.getById` 缓存加载、预热并发加载；
- **Write（写锁）**：写独占。`SeatHandler` 座位操作、`TicketRemainNumberHandler` 余票操作、`UserService` 注册写。

**风险**：锁类型用错（如把写操作标成 Read）会导致并发写不受保护。
**优化**：默认 Reentrant，写场景显式用 Write，读预热用 Read，通过代码评审约束。

---

### 技术点 D：注解式 @ServiceLock —— 如何做到对业务零侵入

**是什么**：`@ServiceLock` 注解声明在方法/类上，由 `ServiceLockAspect` 环绕通知自动"加锁 → 执行业务 → 解锁"。

**为什么用注解（对比编程式）**：
- **声明式、零侵入**：业务方法体不出现任何加锁代码，只需要一行注解；业务方不用知道锁怎么拿、怎么释放、超时怎么处理；
- **语义清晰**：`@ServiceLock(lockType=Write, name=SEAT_LOCK, keys={"#programId","#ticketCategoryId"})` 一眼看懂锁什么、锁粒度多大；
- **类级支持**：类注解作为默认配置，方法级注解优先覆盖（与 `@Transactional` 语义一致），且方法已标注时类级切面直接放行避免双重加锁。

**怎么做**（代码锚点 `ServiceLockAspect.around`）：
```
解析 @ServiceLock 注解
  → LockInfoHandleFactory 获取锁信息处理器 → 用 SpEL 动态拼锁 key
  → ServiceLockFactory.getLock(lockType) 获取对应锁
  → tryLock(lockName, timeUnit, waitTime) 带超时尝试加锁
  → 成功：joinPoint.proceed() 执行业务，finally 中 unlock
  → 失败：走 LockTimeOutStrategy（默认 FAIL 快速失败）+ 兜底抛异常
```

**风险**：锁 key 需要正确拼出"互斥粒度"——拼错（如漏掉参数）会导致不同请求互斥成一把大锁，或本该互斥却各自为政。
**优化**：keys 用 SpEL 引用方法参数（`#orderCancelDto.orderNumber`），粒度由业务精确控制。注解锁的粒度由 SpEL 在运行时决定，已足够灵活。

---

### 技术点 E：编程式 ServiceLockTool —— 什么时候用注解外的入口

**是什么**：`ServiceLockTool` 提供 `execute(taskRun, name, keys)`、`submit(taskCall, ...)`、`getLock(...)` 等编程式方法，内部组合 `LockInfoHandleFactory` + `ServiceLockFactory`。

**为什么需要编程式（注解表达不了的场景）**：
- **一个方法内动态获取多把锁**：注解只能按方法粒度加锁；编程式可以在方法内部对不同参数加不同粒度的锁；
- **需要锁对象本身**：如 `ProgramOrderV2Strategy` 要拿到 `RLock` 逐个 `tryLock`、逆序释放，注解无法表达这种"获取多个锁"的流程；
- **返回值/自定义流程**：`submit` 支持有返回值任务。

**怎么设计（与注解的互斥一致性）**：
- 两个入口共用 `getLockPrefixName()` + 同一套 lockName 拼接规则 → **同一业务名在注解入口和编程式入口生成的锁名一致**，跨入口互斥生效，不会出现"注解锁了、工具没锁"的漏洞。

**风险**：编程式容易忘记 finally 释放锁。
**优化**：`execute`/`submit` 内部已用 try/finally 包好，调用方无需手动释放。

---

### 技术点 F：加锁失败/超时怎么办 —— LockTimeOutStrategy

**是什么**：`@ServiceLock` 提供 `waitTime`（默认 10s）等待加锁；超时后走 `lockTimeoutStrategy`，当前默认 `LockTimeOutStrategy.FAIL`。

**为什么选"快速失败"而不是无限等待**：
- **避免雪崩**：高并发抢锁时，无限阻塞会让请求堆积、线程池打满，反过来拖垮服务；
- **体验可控**：用户得到明确的"请求频繁"错误，而不是卡死；
- **语义简单**：抢不到锁就说明有人在处理同资源，直接失败让客户端重试/提示，比默默等待更可预期。

**怎么做**：
- `LockTimeOutStrategy.FAIL.handler(lockName)` 处理超时；
- **兜底防呆**：即使超时策略实现异常不抛，切面也**绝不进入业务方法**（代码注释：绝不在未持有锁的情况下执行业务）——这是正确性底线；
- 支持自定义超时策略：`customLockTimeoutStrategy` 指定一个同签名方法，超时时走业务自定义兜底。

**风险**：快速失败需要业务侧配合（客户端重试、提示），否则用户感知差。
**优化**：框架内已保证"未持锁必不执行业务"，业务侧做友好提示。

### 技术点 G：锁与事务的时序竞态 —— 为什么"加锁先于事务、释放晚于事务提交"（本主题最深点）

**是什么**：`@ServiceLock` 与 `@Transactional` 同时标注时，通过 `@Order(-10)` 控制切面顺序，保证：**加锁发生在事务开启之前，释放发生在事务提交之后**。

**为什么这个时序关键**：
- 假设顺序反了——**先开事务，再在事务内加锁**：
  - 线程 A 开启事务，加锁，改订单状态（未提交）；
  - 线程 A 提交前释放锁；
  - 线程 B 拿到锁，读到 A 的**未提交**数据（或基于旧值操作），产生竞态错误；
- 假设锁在**事务提交前释放**：同样，B 在 A 提交前进入，读到的可能是 A 事务中间态 → 重复下单、状态覆盖、超卖等并发问题；
- 正确顺序：**加锁 → 事务开启 → 业务 → 事务提交 → 释放锁**。这样 B 只有在 A 完全提交后才能进入，读到的一定是提交后的数据。

**怎么做（代码锚点）**：
- `ServiceLockAspect` 标注 `@Order(-10)`；
- Spring 事务拦截器（`TransactionInterceptor`）默认 `Ordered.LOWEST_PRECEDENCE`（整数最大值，优先级最低）→ 数值越小优先级越高、越处于代理链外层；
- 切面执行顺序：`RepeatExecuteLimit(-11)` → `ServiceLock(-10)` → 事务拦截器（最内层）→ 业务方法；
- `@Around` 环绕语义：ServiceLock 在业务**之前**加锁（`proceed()` 调用前，早于事务开启）、在业务**之后**解锁（finally，晚于事务提交）。

**风险与边界（代码注释已明示，面试主动讲）**：
- 这个保证**仅在加锁方法和 `@Transactional` 标注在同一个方法**时成立；
- 若 `@Transactional` 标注在**更外层方法**，或发生**自调用**（绕过代理），锁可能在事务提交前释放 → 竞态回归；
- 切面里还做了**防御性检测**：`TransactionSynchronizationManager.isActualTransactionActive()` 为 true 时打警告日志，提示锁可能在已开启事务内获取。

**优化**：约定"锁与事务标在同一方法"；切面检测到异常时序时告警。

### 技术点 H：可重入 / 公平 / 读写锁的底层原理（Redisson 实现）

**是什么**：本项目锁模型直接使用 Redisson 原生实现，需要能讲清底层原理。

**可重入锁（Reentrant）**：
- Redisson 用 **hash 结构**存储：key = 锁名，field = 持有线程 id，value = 重入计数；
- 加锁时：字段不存在则 `hset` + 设过期；已存在且是同一线程则 `hincrby` 计数 +1（可重入）；其他线程则等待；
- 释放时：计数 -1，减到 0 才真正删除锁；
- 为什么业务需要：`cancel()` 里先拿锁再调内部方法，方法内可能又需要同一把锁，不可重入会死锁。

**公平锁（Fair）**：
- Redisson 在锁上加一个**等待队列**（有序集合/队列），按请求到达顺序排队，逐个唤醒；
- 对比普通锁：普通锁是"谁先抢到谁先用"，可能饥饿；公平锁保证先来先得。
- **本项目业务未使用**：抢票场景不关心饥饿，且公平锁排队开销影响吞吐，留作能力储备。

**读写锁（Read/Write）**：
- 一个 key 存两种锁状态：写锁存在时读锁/写锁都互斥；只有读锁时可并发读；
- 本项目场景：`ProgramService.getById` 缓存加载用 Read（多个线程可同时加载不同节目），`SeatHandler` 座位写用 Write（互斥）。

**风险**：读写锁是"读共享、写独占"，业务上必须保证读操作确实只读，否则用读锁会放行写竞态。
**优化**：按数据访问特征选型（读多写少用 Read/Write，纯互斥用 Reentrant）。

### 技术点 I：watchdog 自动续期 —— 为什么需要、原理是什么

**是什么**：Redisson 加锁默认 leaseTime 为 -1（不设固定过期）时，会启动一个**后台 watchdog** 定时续期。

**为什么需要**：
- 若设置固定过期时间：业务执行时间 > 过期时间 → 锁先释放，别人拿到锁，**业务仍在跑** → 竞态；
- 若完全不设过期：进程崩溃锁永远不释放 → **死锁**；
- watchdog 折中：默认 30s 有效，每 1/3（约 10s）续期一次，只要业务还在执行就续期；进程崩溃后不再续期，锁自然过期释放。

**怎么做**：Redisson 内部使用 Lua 脚本 `pexpire` 重置过期时间，由持有锁的线程续期（只有持锁者能续，避免误续他人锁）。

**风险**：watchdog 不是万能——业务线程长时间 STW（GC）或网络分区，续期可能失败，锁仍会过期。
**优化**：关键业务也可显式设置合理的 leaseTime（不依赖续期），两者权衡。

### 技术点 J：锁 key 设计 —— 粒度、命名、隔离

**是什么**：锁 key 由 `AbstractLockInfoHandle` 统一拼接，格式：
```
{环境前缀}-SERVICE_LOCK:{业务名}:{SpEL解析出的key值}
示例：default-SERVICE_LOCK:UPDATE_ORDER_STATUS_LOCK:订单号
```

**为什么这么设计**：
- **粒度由 keys 控制**：锁"订单号"就是单订单互斥；锁"programId+ticketCategoryId"就是档位粒度互斥（`SeatHandler`）；
- **命名空间隔离**：`SERVICE_LOCK` 与 `REPEAT_EXECUTE_LIMIT` 前缀分离，锁与幂等互不干扰；
- **环境隔离**：`prefixDistinctionName` 前缀防止本地/测试/生产环境锁 key 冲突。

**风险**：key 过长会浪费内存；key 语义设计错会导致锁粒度过大（性能）或过小（互斥失效）。
**优化**：keys 用业务最小维度，参考 `#orderCancelDto.orderNumber` 这种精确到实体的设计。

### 技术点 K：锁 vs 幂等（RepeatExecuteLimit）—— 为什么是两个东西、顺序怎么排

**是什么**：框架里除了 `@ServiceLock`，还有一套 `@RepeatExecuteLimit`（幂等拦截）。两者共用 LockInfo 体系但**前缀不同**。

**为什么是两套能力**：
- **锁解决"并发互斥"**：同一资源同一时刻只能一个线程执行（取消 vs 支付）；
- **幂等解决"重复执行"**：同一请求（如同一条 Kafka 消息、同一次用户点击）只允许生效一次；
- 场景区分：Kafka 重复消费同一订单消息 → 用 `@RepeatExecuteLimit`（`CREATE_PROGRAM_ORDER_MQ`）；并发取消+支付 → 用 `@ServiceLock`。

**顺序设计**（`RepeatExecuteLimitAspect` 是 `@Order(-11)`，比锁更靠外）：
- 幂等拦截**先执行**：重复请求在加锁前就被挡掉，**省掉无谓的加锁开销**；
- 幂等标记**写入晚于事务提交**：`RepeatExecuteLimitAspect` 里用 `writeIdempotentFlagAfterCommit` 注册 `afterCommit` 回调，业务成功且事务提交后才打标，避免"事务回滚了但幂等标记已写"导致后续被误判为重复。

**风险**：两者职责混淆会顾此失彼——只用幂等防不住并发竞态，只用锁防不住重复执行。
**优化**：按场景叠加使用（如 `OrderService.cancel` 同时标 `@RepeatExecuteLimit` + `@ServiceLock` + `@Transactional`）。

---

### 技术点 L：锁粒度设计实例 —— 为什么 V2 下单要按档位拆锁

**是什么**：`ProgramOrderV2Strategy` 放弃对整个节目加一把大锁，改为**按 ticketCategoryId（票价档位）分别加锁**：每个档位一把本地 ReentrantLock（`LocalLockCache`，Caffeine 缓存锁对象）+ 一把 Redis RLock，全部获取成功后再下单。

**为什么拆粒度**：
- 同一节目的不同票价档位（如 199 元档、399 元档）可以**独立并发下单**；
- 若锁整个节目，不同档位的下单互相阻塞，并发度被锁卡死；
- 拆到档位粒度后，不同档位的请求并行，同档位才互斥，**并发度大幅提升**。

**怎么做（代码锚点）**：
- 从入参座位列表提取**去重、排序**的 ticketCategoryId 列表；
- 第一轮：构造所有本地锁 + 分布式锁列表（此时未申请）；
- 第二轮：先本地锁全部 tryLock（限时 3s），任一失败标记并停止；
- 第三轮：本地锁全成功后，再逐个 tryLock 分布式锁；
- 任一层失败抛 `SERVICE_LOCK_FAIL`；成功则执行 `programOrderService.create()`；
- **finally 逆序释放**：先释放分布式锁、再释放本地锁，避免锁交叉依赖死锁。

**风险**：本地锁 + 分布式锁两轮获取，锁等待超时会导致请求失败；多锁获取有死锁风险。
**优化**：统一获取顺序 + 逆序释放；3s 限时快速失败。

### 技术点 M：极端情况与降级（怎么办层汇总）

| 场景 | 怎么办 |
|------|--------|
| 加锁超时（拿不到锁） | `LockTimeOutStrategy.FAIL` 快速失败 + 兜底抛异常，**绝不无锁执行业务** |
| 业务执行超锁时长 | 依赖 Redisson watchdog 自动续期；或显式设置合理 leaseTime |
| 进程崩溃 | 锁带过期时间，watchdog 停止续期后自然释放，不死锁 |
| 锁误删他人 | Redisson 用 Lua 校验持有者 value 后删除，框架层已防 |
| 主从切换丢锁 | Redis 主从的固有限制；项目用幂等/对账兜底，接受极小概率 |
| 自调用绕过代理 | 锁切面失效，约定"锁与事务标在同一方法"，切面检测实际事务状态并告警 |
| 多锁获取 | 统一获取顺序 + finally 逆序释放，防死锁 |
| 锁 key 冲突 | `SERVICE_LOCK`/`REPEAT_EXECUTE_LIMIT` 前缀 + 业务名 + 环境前缀三重隔离 |
| 锁粒度过大 | 按业务最小维度拆 key（V2 按档位拆锁），提升并发度 |

## 4. 重点准备追问链（三层连问）

### 追问链 1：从"为什么 @Order(-10)"出发
- **第一层**：为什么加锁要在事务开启之前？
  - 答：否则锁释放早于事务提交，另一个线程会读到未提交的数据，产生重复下单/状态覆盖/超卖。
- **第二层**：Spring 里怎么保证这个顺序？
  - 答：`ServiceLockAspect` 标 `@Order(-10)`，事务拦截器默认 `LOWEST_PRECEDENCE`（最小优先级），数值越小越在代理链外层 → 锁切面先于事务进入、后于事务退出。
- **第三层**：什么情况下这个保证会失效？
  - 答：`@Transactional` 标在更外层方法，或发生自调用绕过代理；框架对此有防御性检测（`isActualTransactionActive` 告警）。

### 追问链 2：从"为什么不自己写 SETNX"出发
- **第一层**：SETNX 为什么不能直接用？
  - 答：有死锁、误删、不可重入、主从丢锁四个坑。
- **第二层**：误删锁具体怎么发生？
  - 答：A 锁超时释放，B 拿到锁，A 执行完 DEL 把 B 的锁删了 → 两个线程同时"持有锁"。
- **第三层**：那 Redisson 怎么解决？
  - 答：释放用 Lua 脚本校验持有者标识再删；加锁用单命令原子操作；可重入用 hash 计数。

### 追问链 3：从"锁和幂等区别"出发
- **第一层**：锁和幂等是同一个东西吗？
  - 答：不是。锁解决并发互斥，幂等解决重复执行。
- **第二层**：什么时候用哪个？
  - 答：Kafka 重复消费同一订单 → 幂等（`@RepeatExecuteLimit`）；并发取消+支付 → 锁（`@ServiceLock`）。
- **第三层**：为什么幂等切面排在锁外面？
  - 答：重复请求先被幂等拦截，省掉无谓加锁；幂等标记通过 afterCommit 晚于事务提交写入，避免事务回滚后误判重复。

### 追问链 4：从"读写锁"出发
- **第一层**：项目里哪里用了读写锁？
  - 答：`ProgramService.getById` 缓存加载用 Read，`SeatHandler` 座位写用 Write。
- **第二层**：读写锁原理？
  - 答：读锁可并发、写锁互斥，内部用一个 key 区分读/写状态。
- **第三层**：为什么不都用可重入锁？
  - 答：读操作并发无害，用互斥锁会浪费并发度；读写锁让并发读不被阻塞，只挡写。
