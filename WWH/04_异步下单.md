# 主题四：Lua + Redis + Kafka 异步下单链路（V4）—— 面试深挖分析

> 基于"业务问题 → 技术方案 → 设计原因 → 实现方式 → 遇到问题 → 优化方案 → 极端情况处理"链路。
> 每个技术点按「是什么 / 为什么 / 怎么办」三层组织。本版仅分析 **V4 异步下单方案**，代码锚点均经 codegraph 核实。

---

## 1. 项目背景

### 业务场景
抢票系统的**下单瞬间**是全网最高压的时刻：热门节目开票，几十万用户同时点"立即购买"。核心挑战：
- **超卖**：余票有限，并发下绝不能卖超；
- **集中**：所有流量集中在少数热门节目；
- **响应**：用户要尽快拿到结果，不能让请求卡在 DB 写入上。

### 版本演进：V1/V2 → V3 → V4（为什么最终是 V4）
下单链路经历了多版本迭代，每版解决上一版的核心问题（代码锚点 `ProgramOrderService.create/createNew` 注释）：
- **V1/V2（同步 + 无校验 Lua）**：请求线程内完成校验 + 落库；但校验在 Java 侧、扣减在 Lua 侧，**跨版本并发存在超卖窗口**——这是真实踩过的坑；
- **V3（同步 + 带校验 Lua）**：把校验收敛进带校验的 Lua 脚本（`programDataCreateOrderResolution.lua`），一次原子完成"校验余票/座位/价格 + 扣减"，**消除超卖窗口**；但仍是同步路径，DB 落库占据请求线程，RT 长；
- **V4（异步 + Kafka）**：在 V3 的原子扣减基础上，把 DB 写入剥离到 Kafka 消费端异步完成，**释放请求线程、RT 最短、吞吐最高**。

### 为什么需要重新设计（V4 异步化）
把下单拆成"**锁内只做原子扣减 + 锁外异步建单**"：
1. **Lua 原子扣库存**：锁内仅执行 Redis Lua 脚本（校验余票/座位/价格 + 锁座 + 扣减），用内存速度扛并发、天然防超卖；
2. **Kafka 异步建单**：锁外发 Kafka 消息，请求线程立即返回，DB 落库放到消费端异步完成；
3. **延迟队列兜底**：超时未支付自动取消 + 库存回补。

> 一句话背景叙述（面试开场用）：
> "同步下单时 DB 扣库存扛不住开票瞬间的并发，而且历史上 V1/V2 把校验放 Java、扣减放 Lua，跨版本并发存在超卖窗口。V3 先把校验收敛进带校验的 Lua，消除超卖；V4 再把它异步化——本地锁内仅执行 Redis Lua 原子扣减（校验余票/座位/价格 + 锁定座位 + 扣减余票），锁外发 Kafka 消息异步建单，请求线程立即返回；再通过延迟队列做超时未支付订单的自动取消与库存回补，保证不超卖、最终一致。"

## 2. 整体架构

### V4 下单链路
```
用户点击下单（program-service）
  → ProgramOrderV4Strategy.createOrder()
      → @RepeatExecuteLimit（幂等：同一 userId+programId 防重复提交）
      → compositeContainer 组合校验链（登录/限购/购票人/布隆过滤器等）
      → baseProgramOrder.localLockExecute()：按 ticketCategoryId 加本地锁
          └─ 锁内回调：createOrderOperateProgramCacheResolution()
              ├─ 预热座位/余票缓存（缓存缺失时才预热，避免锁内长耗时）
              ├─ 选座：Lua 单次原子校验+锁定（programDataCreateOrderResolution.lua）
              │        不选座：应用层匹配相邻座位 → Lua 校验+锁定（抢占重试）
              └─ Lua 内：校验余票/座位/价格 → 锁定座位（未售→已锁）→
                          HINCRBY 扣余票 → 写扣减流水
      → 锁外 createNewAsyncAfterLock() → doCreateV2()
          ├─ 预生成订单号（uidGenerator.getOrderNumber(userId)，含基因）
          ├─ createOrderByMq()：发 Kafka 建单消息（CountDownLatch 等待发送结果，失败回滚 Redis）
          └─ delayOrderCancelSend：投递延迟取消消息

Kafka（order-service）
  → CreateOrderConsumer（@KafkaListener，concurrency=12）
      → 延迟 60s 消费（给 Redis 数据同步留时间）
      → orderService.createMq()（@RepeatExecuteLimit 防重复建单）
          → doCreate() 事务落库（订单/购票人/购票人记录/订单节目）

延迟队列（自研封装 Redisson RDelayedQueue）
  → DelayOrderCancelConsumer：超时未支付 → orderService.cancel() → 回补库存
  → DelayOperateProgramDataConsumer：取消解锁座位/支付标记已售
  → 异常补偿 DelayOrderCancelExceptionMessageHandler：消费失败延迟 1s 重投

支付回调（order-service）
  → operateProgramData：座位 LOCK→SOLD（支付）/ LOCK→NO_SOLD（取消）+ 库存增减
```

### 核心设计要点（V4 区别于同步路径）
- **锁内只放必须互斥的操作**：Lua 扣减（临界区）在锁内；**Kafka 发送在锁外**——避免同步等待 Kafka 发送确认拉长锁持有时间、放大锁竞争失败（70005）；
- **缓存预热也做了优化**：座位缓存已预热时跳过全量拉取（每档 2 万 field，全量读+反序列化开销大），避免在锁内做长耗时操作。

## 3. 核心技术方案拆解

### 技术点 A：V1/V2 的超卖窗口 —— 为什么"Java 校验 + Lua 扣减"会超卖（踩过的坑）

**是什么**：历史 V1/V2 版本把"校验"放在 Java 侧、"扣减"放在无校验的 Lua 侧，两步之间存在并发窗口。

**为什么会超卖（逐层拆）**：
- Java 侧先查余票/座位，判断"够不够"；
- 判断通过后，再调 Lua 扣减；
- 两个请求并发：A 查到余票 1 张（够），B 也查到余票 1 张（够），A 扣减成功（余票 0），B 随后也扣减成功（余票 -1）→ **超卖**；
- 因为校验和扣减不是原子操作，中间有"读到旧值"的窗口。

**怎么发现/怎么改**：
- 通过并发压测/对账发现超卖数据；
- V3 开始把校验**收敛进带校验的 Lua 脚本**——"读余票 → 判断 → 扣减"在同一原子脚本内完成，中间不插入其他命令，窗口消除；
- V4 沿用带校验 Lua，只在此基础上做异步化。

**怎么办（面试主动讲）**：
- 这条演进说明"校验和扣减必须原子"是防超卖的根本，也是为什么项目反复强调 Lua 脚本是最终防线；
- 任何后续优化（异步化、去锁）都不能牺牲"校验+扣减原子"这个底线。

---

### 技术点 B：为什么用本地锁（按档位）而不是全局一把锁

**是什么**：`ProgramOrderV4Strategy` 调用 `baseProgramOrder.localLockExecute()`，**按 ticketCategoryId（票价档位）加本地 ReentrantLock**，锁内执行 Lua 扣减。

**为什么按档位拆锁**：
- 同一节目的不同票价档位（如 199 元、399 元档）可以**独立并发下单**；
- 若锁整个节目，不同档位的下单互相阻塞，并发度被锁卡死；
- 拆到档位粒度后，不同档位并行、同档位才互斥，**并发度大幅提升**。

**为什么用本地锁（JVM 内）而不是分布式锁**：
- 本地锁够用：**并发安全的最终底线是带校验的 Lua 原子脚本**，本地锁只是"快速失败"手段，防止同 JVM 内大量请求同时冲进 Lua 造成 Redis 压力放大；
- 本地锁无网络开销、无 Redis 依赖，比分布式锁轻得多；
- 本地锁先于分布式锁获取、后释放，形成相反的释放顺序，避免锁依赖顺序不一致导致死锁。

**怎么做**（代码锚点 `BaseProgramOrder.localLockExecute`）：
- 从座位列表提取**去重、排序**的 ticketCategoryId；
- 为每个档位构建本地锁 key（前缀 + programId + ticketCategoryId），存入列表；
- 逐个 `tryLock(3s)`，任一失败标记并快速失败（`SERVICE_LOCK_FAIL`）；
- 全部获取成功后执行锁内回调（Lua 扣减）；
- finally **反向释放**（后加的先释放）。

**风险**：本地锁只对单实例有效，多实例并发仍可能同时进入（靠 Lua 原子性兜底）。
**优化**：V4 认为 Lua 原子校验是最终防线，本地锁只做流量收敛，不做正确性依赖。

---

### 技术点 C：为什么用 Lua 脚本做库存扣减、为什么原子

**是什么**：锁内执行 Redis Lua 脚本（`programDataCreateOrderResolution.lua`），一次 EVAL 内完成"校验余票/座位/价格 + 锁定座位 + 扣减余票 + 写流水"。

**为什么用 Lua（而不是 Java 代码 + Redis 命令）**：
- **原子性**：Redis 单线程执行 Lua 脚本，**脚本执行期间不插入任何其他命令** → 中间没有并发窗口，从"读余票"到"扣减"整体原子，天然防超卖；
- **跨命令条件判断**：Lua 用 `if/else` 根据前一步结果决定后续动作（如余票不足直接返回），并返回自定义错误码；
- **减少网络往返**：一次 EVAL 代替多次 Redis 命令。

**为什么不用 Redis 事务（MULTI/EXEC）**：
- MULTI/EXEC 只是"把命令打包顺序执行"，**不支持中间逻辑判断**——不能在扣减前校验余票再决定是否扣减；
- 事务中途出错不能返回细粒度错误码；Lua 可以。

**怎么做**（代码锚点 `programDataCreateOrderResolution.lua`）：
- KEYS：type、未售座位 hash key、已锁座位 hash key、节目 id、记录 hash key、记录标识、记录类型；
- ARGV：票档 JSON、座位 JSON、购票人列表；
- 错误码：40001 座位不存在 / 40002 已锁定 / 40003 已售 / 40008 价格不一致 / 40010 票档不存在 / 40011 余票不足 / 0 成功；
- 操作顺序：验证 → 锁定座位（hdel 未售 + hmset 已锁）→ 扣余票（HINCRBY -count）→ 写流水记录。

**风险**：脚本逻辑全在 Redis 内，出 bug 排查成本高。
**优化**：脚本集中管理（resources/lua 目录）、错误码统一枚举、关键路径留日志。

---

### 技术点 D：幂等机制 —— @RepeatExecuteLimit 怎么防重复（V4 幂等核心）

**是什么**：V4 下单方法上标 `@RepeatExecuteLimit(keys = {"#userProgramId.userId","#userProgramId.programId"})`，基于 Redisson 分布式锁实现幂等。

**为什么需要幂等（V4 里幂等防什么）**：
- **用户重复提交**：抢票场景用户可能连续点击/前端重试，同一用户同一节目不能下两单；
- **Kafka 重复消费**：消费端建单消息可能重复，不能重复建单。

**怎么做（代码锚点 `RepeatExecuteLimitAspect.executeWithLimit`）**：
- **两层防重锁**：
  - 第一层本地 ReentrantLock（同 JVM 内并发快速失败）；
  - 第二层 Redis Reentrant Lock + `tryLock(0)`（非阻塞快速失败，跨进程互斥）；
- **幂等标记**：`durationTime > 0` 时，业务执行成功后 `setIfAbsent` 写幂等标记并设 TTL，期间相同 name+keys 的请求直接快速失败；
- **标记晚于事务提交写**：`writeIdempotentFlagAfterCommit` 注册 `afterCommit` 回调，事务提交后才写标记——避免"事务回滚但幂等标记已写"导致后续被误判为重复；
- **两种用法**：
  - `durationTime > 0`：防重复执行（Kafka 消费幂等，`CREATE_PROGRAM_ORDER_MQ`）；
  - `durationTime = 0`（默认）：仅防并发（锁持有期间互斥），不写标记，业务完成后相同请求可再执行。

**风险**：幂等窗口（durationTime）内用户想改单会被拒绝。
**优化**：幂等窗口与业务语义对齐（抢票场景提交即锁单，符合预期）。

---

### 技术点 E：防超卖做了哪几层防护

**是什么**：超卖是抢票系统最致命的问题，V4 从入口到扣减做了多层防护。

**多层防护**：
1. **Lua 原子校验 + 扣减**（核心，技术点 A/C）：脚本内先校验余票/座位/价格，再原子扣减，不存在"读了但没扣上"的窗口；
2. **幂等注解（@RepeatExecuteLimit）**（技术点 D）：同一用户同一节目防重复提交；
3. **座位三态流转**：座位在"未售 → 锁定 → 已售"间流转，已锁定/已售的座位再次下单直接拒绝（40002/40003），防止同一座位被卖两次；
4. **价格校验**：入参价格 > 缓存价格直接拒绝（40008），防前端篡改价格；
5. **DB 幂等**：消费端 `createMq` 标 `@RepeatExecuteLimit` + `doCreate` 先查 orderNumber 存在即拒绝，防 Kafka 重复消费导致重复建单。

**为什么需要这么多层**：每一层防不同路径——Lua 防并发竞态、幂等防重复请求、座位状态防同座双卖、DB 防重复落库。缺任何一层都有超卖路径。

**风险**：Lua 脚本是最后防线，若脚本 bug 则全盘皆输。
**优化**：脚本校验逻辑完整、覆盖所有失败分支，测试覆盖脚本各错误码。

### 技术点 F：座位锁定的数据流转 —— 三区 hash 怎么操作

**是什么**：座位状态存在 Redis 三个 hash 中：未售（NO_SOLD）、锁定（LOCK）、已售（SOLD），下单时由 Lua 完成 field 流转。

**怎么做（代码锚点 `programDataCreateOrderResolution.lua`）**：
- **校验**：从"未售 hash"读座位（`hget`），空 → 40001；sellStatus=2 → 已锁定；sellStatus=3 → 已售出；
- **锁定**：`hdel` 从未售 hash 删除座位 field，`hmset` 写入锁定 hash（座位数据 + 绑定购票人）；
- **余票**：`hincrby` 各票档余票 -count；
- **流水**：写扣减记录 `purchase_record`（含各票档 before/after 数量、座位记录）。

**为什么用三个 hash 而不是一个**：
- 未售 hash 用于"选座匹配"（快速列出可选座位）；
- 锁定 hash 用于"支付/取消时定位"（谁锁的、绑定了谁）；
- 已售 hash 用于对账与查询；
- 分区隔离，读多写少各自高效。

**支付/取消的流转**（衔接 `operateProgramData`）：
- 支付成功：锁定 → 已售（LOCK→SOLD）；
- 取消：锁定 → 未售（LOCK→NO_SOLD）+ 余票归还（increaseRemainNumber）。

**风险**：座位数据量巨大时三区 hash 占内存。
**优化**：按节目 + 票档拆 hash key，惰性预热，reset 时清理。

### 技术点 G：选座与不选座两条路径（为什么匹配算法放应用层）

**是什么**：`createOrderOperateProgramCacheResolution` 分两条路径——选座（用户指定座位）和不选座（系统自动匹配相邻座位）。

**选座路径**：候选座位由用户指定，Lua 单次原子校验 + 锁定；
**不选座路径**：
- 应用层从"未售 hash"读取全部未售座位，`matchAdjacentSeats` 按行/列排序匹配相邻座位；
- 候选座位被并发订单抢占（40001/40002/40003）时，**重新匹配并重试**（`AUTO_MATCH_RETRY_TIMES` 次）；
- 仅对"候选座位被抢占"重试；其他错误（余票不足/价格不一致等）直接失败。

**为什么匹配算法放应用层（而不是 Redis 内）**：
- 未售座位集合数据量大（每档 2 万 field），在 Redis 内全量 `hvals` + 排序会**阻塞 Redis 主线程**、拖垮全局；
- 应用层读取 + 排序，Redis 只负责最终的原子校验锁定，职责清晰。

**风险**：不选座路径"读取 + 匹配 + Lua 校验"是两步操作，并发下候选座位可能被抢占。
**优化**：抢占后自动重试匹配，最终正确性仍由 Lua 原子校验裁决。

---

### 技术点 H：为什么用 Kafka 异步建单（对比同步 / 线程池）

**是什么**：锁内扣完 Redis 库存后，**锁外**发 Kafka 建单消息，order-service 消费端异步落库。

**为什么异步（对比同步 RPC / V1-V3）**：
- **请求线程不等待 DB**：同步建单时 DB 写入（多条 insert + 事务）占据请求线程；V4 请求线程发完消息就返回，用户秒级拿到订单号；
- **削峰**：Kafka 天然缓冲，生产端瞬时流量再大，消费端按自己的速度慢慢落库，把开票洪峰平滑掉；
- **解耦**：program-service 不直接依赖 order-service 可用性，消费端挂了消息还在，恢复后继续消费。

**为什么不用线程池**：
- 线程池只能**服务内部**异步，无法跨服务解耦；
- 线程池无持久化，服务重启任务丢失；Kafka 消息持久化，可靠；
- 线程池无削峰能力（内存队列有限），Kafka 可积压缓冲。

**为什么 Kafka 发送放锁外**（V4 的关键设计）：
- 若在锁内同步等待 Kafka 发送确认（网络 IO），会**拉长锁持有时间、放大锁竞争失败（70005）**；
- 所以锁内只做 Lua 原子扣减，锁外再发 Kafka——锁内临界区最小化。

**怎么做**（代码锚点 `createOrderByMq` + `CreateOrderSend`）：
- `createOrderByMq`：发消息 + `CountDownLatch` 同步等待发送结果（10s 超时）——**扣了库存必须确认消息发出**，否则库存扣了但单没建；
- 发送失败回调：`updateProgramCacheDataResolution(..., CANCEL)` **回滚 Redis 缓存**（释放座位、恢复余票）；
- 消费端 `CreateOrderConsumer`：`@KafkaListener(concurrency=12)` 与 topic 分区数一致，每条消息**延迟 60s 消费**（给 Redis 数据同步留时间窗口）。

**风险**：Kafka 发送失败/消费失败需要补偿。
**优化**：发送失败自动回滚 + 消费端幂等 + 对账任务兜底。

---

### 技术点 I：Kafka 消息不丢失 / 不重复 —— 三个层面

**是什么**：Kafka 消息可靠性分生产端、Broker、消费端三端。

**生产端不丢**：
- `KafkaTemplate.send` + `CompletableFuture.whenComplete` 回调确认；失败走 `FailureCallback` 触发 Redis 回滚；
- `CountDownLatch.await(10s)` 同步等发送结果，超时抛 `EXECUTE_TIME_OUT`——保证"扣了库存的消息一定发出或已回滚"。

**Broker 不丢**：topic 多分区 + 副本机制（配置层面），ack 策略确认写入。

**消费端不丢**：
- 消费端 `createMq` 标 `@RepeatExecuteLimit` + `doCreate` 先查 orderNumber 已存在即拒绝——重复消费不会重复建单；
- 消费端延迟 60s 消费，给 Redis 同步留时间。

**重复消费怎么防（消费端幂等）**：
- `@RepeatExecuteLimit(name=CREATE_PROGRAM_ORDER_MQ, keys={"#orderCreateMq.orderNumber"}, durationTime=60)`：同一订单号 60s 窗口内只建一次；
- `doCreate` 里再查一次 orderNumber，双保险。

**风险**：极端情况下消费端一直失败，消息可能重试多次。
**优化**：消费异常记录 + 对账任务重投 + 丢弃超阈值订单进 DISCARD_ORDER（`CreateOrderConsumer` 注释）。

---

### 技术点 J：Kafka 消息丢失 / 建单失败的补偿机制

**是什么**：异步链路中"Redis 扣了但 DB 没落"是必须兜底的场景。

**补偿手段**：
1. **发送失败即时回滚**：`createOrderByMq` 失败回调 → 回滚 Redis（释放座位、恢复余票），库存不白白扣掉；
2. **消费端幂等**：`@RepeatExecuteLimit` + orderNumber 唯一校验，重复消费不重复建单；
3. **对账任务（ReconciliationTask）**：核对 Redis 扣减流水与 DB 落账，发现"扣了没落"的订单记录走补偿（`discardOrderCompensation`）；
4. **丢弃订单（DiscardOrder）**：超过丢弃时间阈值的消息写入 DISCARD_ORDER 并记录原因，供人工/对账处理。

**风险**：对账是最终兜底，若对账本身漏跑则产生脏数据。
**优化**：对账任务定时执行 + 失败告警。

---

### 技术点 K：延迟队列 —— 为什么自研封装一层（核心卖点）

**是什么**：超时未支付订单取消、节目数据延迟操作都依赖延迟消息。底层是 Redisson `RDelayedQueue`，项目在其上自研封装了 `ticketflow-service-delay-queue-framework`。

**Redisson RDelayedQueue 底层原理**：
- 底层是 **zset**（成员=消息，score=到期时间戳）+ 一个 `RBlockingQueue` + 发布订阅通知；
- 到期时 zset 里 score 最小的消息被移到阻塞队列，`blockingQueue.take()` 取出消费；
- 依赖 Redis，消息持久化，进程重启后仍在。

**为什么自研封装（相比直接用 RDelayedQueue）**：
- **单 key 热点**：原生方案所有延迟消息挤在一个 zset，高并发下是单点热点，吞吐受限；
- **分区隔离（isolationRegionCount=5）**：同一 topic 拆成 `topic-0`~`topic-4` 5 个物理分区，生产端 `IsolationRegionSelector` 轮询选择分区写入，消费端按同规则建 5 个 `DelayConsumerQueue` 并行消费 → 分散热点、提升吞吐；
- **统一抽象**：`DelayQueueContext.sendMessage(topic, content, delay, unit)` 统一生产入口；`ConsumerTask` 接口定义消费任务；`DelayQueueInitHandler` 在应用启动时自动注册所有 topic 消费者——业务方只需实现接口。

**双线程池消费模型**（代码锚点 `DelayConsumerQueue`）：
- 监听线程池（1 线程）：`blockingQueue.take()` 阻塞取出到期消息；
- 工作线程池（可配置 core/max）：并行执行 `ConsumerTask.execute()`；
- 为什么双池：`take()` 不能并发（单线程监听），取出后交给工作池处理，避免阻塞新到期的消息。

**风险**：分区数（isolationRegionCount）生产端与消费端必须一致，否则消息留在队列无人消费。
**优化**：分区数集中配置、启动校验生产消费对齐。

---

### 技术点 L：延迟消息的可靠性 —— 消费失败 / 丢失怎么办

**是什么**：延迟消息发出去后可能遇到消费失败、进程宕机等异常。

**可靠性设计**：
- **消息持久化**：RDelayedQueue 底层在 Redis，进程重启后消息不丢；
- **幂等消费记录**：`DelayOrderCancelConsumer` 消费前先查消息消费记录（`apiDataClient.getMessageConsumerByMessageId`），已成功消费（CONSUMER_SUCCESS）直接跳过 → 重复消费安全；
- **异常补偿重投**：`DelayOrderCancelExceptionMessageHandler` 处理取消失败的补偿逻辑——异常时把消息**延迟改为 1 秒重投**（立即消费），而非按原始延迟时间重等；
- **对账兜底**：消费记录缺失时由消息对账层重投；`cancel` 本身幂等（`@RepeatExecuteLimit` + `@ServiceLock`），重复取消安全；
- **api-data 故障不阻断**：查询/写入消费记录失败不阻断取消，靠幂等注解兜底重复消费安全。

**风险**：无限重投可能造成消息风暴。
**优化**：消费失败记录 CONSUMER_FAIL + 次数累加，超过阈值丢弃/人工处理。

---

### 技术点 M：超时取消与库存回补 —— 完整链路

**是什么**：用户下单锁定座位、扣减余票后不支付，延迟队列到期自动取消并回补库存。

**完整链路**：
```
下单时 → delayOrderCancelSend.sendMessage()（投递延迟取消消息，延迟=支付超时时间）

到期 → DelayOrderCancelConsumer.execute()
  → 幂等检查（消息消费记录）→ orderService.cancel()
      → @RepeatExecuteLimit + @ServiceLock + @Transactional（防并发取消+支付）
      → updateOrderRelatedData：订单状态 → CANCEL
      → 通知 program-service 回补库存

库存回补 → DelayOperateProgramDataConsumer / operateProgramData
  → 座位 LOCK → NO_SOLD（解锁）
  → 余票 increaseRemainNumber（归还）
  → 缓存：Redis Stream 广播 → 本地缓存失效
```

**支付与取消撞车怎么防**：
- `cancel()` 上 `@RepeatExecuteLimit`（防重复取消）+ `@ServiceLock`（防并发取消+支付同时进入）；
- `operateProgramData` 校验座位当前状态：只有 LOCK 状态才能流转；已是 SOLD（支付成功）的座位幂等跳过，不会误回补。

**风险**：延迟消息丢失则订单永远不取消，座位被锁死。
**优化**：延迟队列持久化 + 异常重投 + 对账任务兜底。

---

### 技术点 N：整条链路的数据一致性 —— 强一致还是最终一致

**是什么**：扣库存（Redis）→ 建单（DB）→ 支付（回调）→ 取消回补，跨 Redis/Kafka/DB 多个存储，无法用单库事务保证。

**一致性策略（最终一致）**：
- **下单阶段**：Redis Lua 原子扣减（权威）+ Kafka 发送失败即时回滚 → 保证"要么扣了且消息发出，要么回滚"；
- **建单阶段**：消费端幂等（@RepeatExecuteLimit + orderNumber 唯一）→ 重复消费不重复建单；
- **支付/取消阶段**：座位状态机 + @ServiceLock 防并发 + 幂等容忍终态；
- **对账收敛**：定时对账核对 Redis 流水与 DB 落账，发现差异补偿（discardOrderCompensation）。

**为什么不追求强一致**：跨 Redis/Kafka/DB 的强一致需要分布式事务（2PC/Seata），在抢票高并发场景下性能和可用性代价过高；通过"幂等 + 状态机 + 对账"把窗口收敛到最终一致。

**风险**：对账窗口内存在短暂不一致（如已扣库存未落 DB）。
**优化**：对账任务 + 丢弃订单记录 + 人工处理通道。

## 4. 重点准备追问链（三层连问）

### 追问链 1：从"为什么用 Lua"出发
- **第一层**：为什么用 Lua 做库存扣减？
  - 答：Redis 单线程执行 Lua 天然原子，一次脚本内完成校验+扣减，防超卖。
- **第二层**：为什么不用 Redis 事务（MULTI/EXEC）？
  - 答：事务不能中间判断逻辑、不能返回细粒度错误码；Lua 可以 if/else 分支 + 自定义错误码。
- **第三层**：脚本里做了哪些校验？
  - 答：余票校验、座位状态（未售/锁定/已售）、价格校验，失败返回 40001~40011。

### 追问链 2：从"V1/V2 超卖"出发
- **第一层**：你们真的踩过超卖的坑吗？
  - 答：踩过。V1/V2 校验在 Java、扣减在无校验 Lua，跨版本并发存在超卖窗口。
- **第二层**：怎么发现的？
  - 答：并发压测/对账发现余票和订单数对不上。
- **第三层**：怎么改的？
  - 答：V3 把校验收敛进带校验的 Lua，校验+扣减原子化，窗口消除；V4 在此基础上异步化。

### 追问链 3：从"为什么用本地锁"出发
- **第一层**：V4 用什么锁？
  - 答：按 ticketCategoryId 拆的本地 ReentrantLock。
- **第二层**：为什么不用分布式锁？
  - 答：并发安全最终由 Lua 原子脚本保证，本地锁只是快速失败/流量收敛手段，无网络开销。
- **第三层**：多实例并发怎么办？
  - 答：本地锁只收敛单实例，跨实例仍靠 Lua 原子校验兜底，不会超卖。

### 追问链 4：从"幂等"出发
- **第一层**：V4 怎么防重复提交？
  - 答：@RepeatExecuteLimit，两层防重锁（本地 + Redis）+ 幂等标记。
- **第二层**：幂等标记什么时候写？
  - 答：afterCommit，事务提交后才写，避免事务回滚后误判重复。
- **第三层**：durationTime=0 和 >0 区别？
  - 答：>0 防重复执行（Kafka 消费幂等）；=0 仅防并发，业务完成后可再执行。

### 追问链 5：从"为什么用 Kafka"出发
- **第一层**：为什么下单要异步化？
  - 答：DB 落库慢、扛不住并发，异步后请求线程不等待，还能削峰解耦。
- **第二层**：为什么不用线程池？
  - 答：线程池只服务内部异步，无法跨服务解耦、无持久化、无法削峰。
- **第三层**：为什么 Kafka 发送放锁外？
  - 答：锁内等待 Kafka 确认会拉长锁持有时间、放大锁竞争失败（70005）；锁内只做 Lua 扣减。

### 追问链 6：从"取消和支付撞车"出发
- **第一层**：用户取消和支付同时发生怎么办？
  - 答：cancel 上 @ServiceLock 互斥 + 座位状态机校验。
- **第二层**：状态怎么流转？
  - 答：LOCK → SOLD（支付）/ LOCK → NO_SOLD（取消），终态幂等跳过。
- **第三层**：库存会重复回补吗？
  - 答：座位状态机保证只有 LOCK 状态才流转，SOLD 终态幂等跳过，不会重复。
