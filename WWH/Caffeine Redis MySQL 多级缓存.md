# Caffeine + Redis + MySQL 多级缓存

## 架构动机

**Q：你们缓存为什么分两层?Redis 之上再加 Caffeine 的收益是什么?**

A：两级缓存主要是为了降低访问成本。Redis 作为分布式缓存解决多实例共享问题，但每次访问仍然需要网络通信和序列化；Caffeine 是 JVM 内本地缓存，可以直接内存读取，延迟更低。加入 Caffeine 后，热点数据可以直接在本地命中，大量请求不会访问 Redis，降低 Redis 的压力。整体链路就是先查 Caffeine，未命中再查 Redis，Redis 也没有数据时才访问数据库。

------

**Q：Caffeine 层主要缓存哪些数据?为什么适合放本地?**

A：本地缓存主要存放节目相关的基础信息，比如节目详情、分类、场次、票档列表等。选择这些数据是因为它们具有读多写少、变化频率低、数据量可控的特点，同时又是用户访问详情页和下单流程中的高频数据，放本地收益比较明显。像实时余票这种强一致要求高、变化频繁的数据不会放 Caffeine，而是放在 Redis 中，通过 Lua 保证原子更新。

------

**Q：多级缓存的读链路?命不中怎么回源?回源数据怎么填回各层?**

A：查询时按照 Caffeine → Redis → MySQL 的顺序逐级访问。Caffeine 命中直接返回；未命中查询 Redis；Redis 也没有数据时访问数据库，并将结果回填 Redis 和 Caffeine。Caffeine 使用 LoadingCache 的加载机制，在 miss 时触发加载逻辑，同一个 key 多个线程同时请求时只有一个线程执行加载，其他线程等待结果，可以减少缓存击穿问题。

------

**Q：余票放本地缓存，各实例间会不一致，这怎么解决?**

A：实时余票不会放本地缓存，因为它变化频繁且一致性要求高。本地缓存主要用于变化较少的基础数据。对于确实需要本地缓存的数据，我们采用失效通知机制，而不是主动同步数据。数据发生变化时，更新方向 Redis Stream 发布一条缓存失效消息，各实例监听消息后删除自己的 Caffeine 缓存，下次请求重新从 Redis 或数据库加载。这样避免了多实例之间维护复杂的数据同步关系，只保证最终一致。

## Redis Stream 失效广播

**Q：你们怎么让集群所有实例的本地缓存实时失效?为什么用 Redis Stream?**

A：节目数据发生变更时，写库成功后会同时删除 Redis 中对应缓存，并向 Redis Stream 发送一条带节目 ID 的失效消息。所有实例监听同一个 Stream，收到消息后删除自己本地 Caffeine 中对应的 key，下次请求重新加载。选择 Stream 是因为本地缓存失效本质是广播通知，需要每个实例都能收到消息，而 Stream 可以持久化消息，避免实例短暂不可用导致失效事件丢失。

------

**Q：Redis 的 Pub/Sub 做不到吗?具体差在哪?**

A：Pub/Sub 更适合实时通知，不适合作为可靠消息机制。它的问题是消息不持久化，发布时没有消费者会直接丢失；消费失败没有确认和重试机制；实例重启期间也无法补消费。缓存失效虽然有 TTL 兜底，但失效消息可靠性越高，不一致窗口越小。Stream 会保存消息，消费者可以按消息 ID 继续读取，可靠性更高。

------

**Q：Redis Stream 相比 Pub/Sub、List 的本质区别是什么?**

A：Pub/Sub 是即时广播模型，消息发送后不保存；List 是简单队列模型，一个消息通常只会被一个消费者消费；Stream 更像一个追加日志，消息有唯一 ID，可以持久化保存，并支持多个消费者独立读取。对于缓存失效场景，关键是同一条失效消息需要被多个实例分别处理，所以 Stream 的多消费者独立消费能力更符合需求。

------

**Q：你们用消费组模式还是广播模式?本地缓存失效为什么适合这种模式?**

A：本地缓存失效使用广播模式。因为每个实例都有自己的 Caffeine 缓存，每个实例都必须收到失效通知。如果使用消费组模式，一条消息只会被其中一个消费者处理，其他实例不会删除自己的缓存，会导致数据不一致。消费组更适合任务分发场景，比如多个 Worker 平分处理任务。

------

**Q：Stream 消费组怎么保证消息不丢?(pending、ack)你们消费端怎么做确认?**

A：消费组模式下，消息读取后会进入 Pending 状态，消费者处理成功后通过 XACK 确认；如果消费者异常退出，未确认消息仍保存在 Pending 列表，可以重新领取处理。这样实现消息处理和确认解耦。不过我们的缓存失效采用广播模式，不依赖消费组 ACK 机制，可靠性主要来自 Stream 持久化和 TTL 兜底。

------

**Q：Stream 从零到能消费，初始化做了什么?重复初始化会怎样?**

A：初始化时会保证 Stream 和消费结构存在。消费组模式下，启动时先检查 Stream 和消费组是否创建，如果不存在则创建；如果多个实例同时启动，重复创建会捕获已存在异常并忽略，保证初始化幂等。广播模式更简单，Stream 在第一次写入消息时自动创建，实例启动后直接读取即可。

------

**Q：消费端靠什么持续监听?线程池怎么配的?为什么拒绝策略选这个?**

A：消费端使用 Redis Stream 监听容器持续拉取消息，收到消息后提交到业务线程池执行。线程池主要用于隔离消息监听和业务处理，避免消费逻辑阻塞监听线程。拒绝策略选择调用者执行，原因是缓存失效消息不能直接丢弃，线程池压力过大时宁可降低消费速度，也要保证消息最终处理。

------

**Q：失效消息万一丢了会怎样?你们能接受的最终一致窗口是多久?有没有兜底?**

A：如果失效消息丢失，本地缓存可能继续保留旧数据，导致一致窗口延长。但本地缓存本身设置了 TTL，超过时间后会自动过期并重新加载，因此不会永久不一致。对于节目这类低频变化数据，我们接受秒级到分钟级的最终一致窗口，正确性最终由数据库保证。

------

**Q：收到失效消息后，请求怎么重建本地缓存?多个请求同时重建怎么防?**

A：失效消息只负责删除本地缓存，不主动回源。后续请求访问时重新走 Caffeine → Redis → MySQL 的加载链路，并把结果重新填回缓存。并发重建主要依靠 Caffeine 的加载机制，同一个 key 同时 miss 时只有一个线程执行加载，其余线程等待结果；同时 Redis 回源增加二次检查，避免多个线程同时访问数据库。

------

**Q：为什么不把新数据直接更新进本地缓存，而选择失效?**

A：因为失效方案更简单可靠。主动更新需要把完整数据广播给所有实例，还要处理消息顺序、数据版本和更新失败等问题；而失效消息只需要携带业务 ID，多个实例重复执行删除也是幂等的。删除后由正常读链路重新加载最新数据，复用了已有缓存逻辑，也避免了并发更新时旧数据覆盖新数据的问题。实际工程中缓存一致性方案通常优先选择删除缓存，而不是主动更新缓存。

## 穿透/击穿/雪崩

**Q：你们哪里最怕缓存穿透?拿什么挡的?布隆过滤器放的是什么数据?**

A：最怕穿透的是节目详情查询这类入口。用户请求一个不存在的节目 ID 时，缓存和数据库都查不到，如果大量这种请求进来，会绕过缓存持续访问数据库。我们在查询链路入口增加了布隆过滤器，启动时加载有效节目 ID，请求进入后先判断 ID 是否可能存在，不存在直接返回，不再访问缓存和数据库。用户侧注册判重也复用了这套组件，把已有手机号加载进去做快速判断。

------

**Q：布隆过滤器原理?误判的后果是什么?误判率怎么控制?**

A：原理是位数组加多个哈希函数。插入元素时，通过多个哈希函数计算位置并置 1；查询时，如果其中一个位置是 0，可以确定不存在；如果全部是 1，只能认为可能存在。所以布隆过滤器的特点是不会漏判，但可能误判。误判的结果是不存在的数据可能继续走缓存和数据库查询，但最终仍然返回不存在，不影响正确性。误判率主要由位数组大小和哈希函数数量决定，我们初始化时根据预计容量和目标误判率计算参数，比如节目数据配置期望容量和 1% 的误判率，由框架自动计算位数组大小和哈希函数数量。

------

**Q：为什么不用"缓存空值"代替布隆过滤器?各自坑在哪?**

A：缓存空值是在查询不到数据时，把空结果写入缓存，短时间内挡住重复请求。它的问题是大量不存在的 ID 会产生大量空缓存，占用内存，同时空值过期时间不好设置，太短拦截效果差，太长又会长期占用资源。布隆过滤器的问题是存在误判，并且删除数据比较困难，需要重新构建。我们选择布隆过滤器主要是因为它占用空间小，适合做大量不存在数据的快速过滤，同时不会误伤正常数据。

------

**Q：什么是缓存击穿?某个热门节目缓存失效的瞬间会发生什么?**

A：缓存击穿是单个热点 Key 失效后，大量请求同时 miss，并发访问数据库，导致数据库压力瞬间升高。抢票场景里的热门节目就是典型风险点，详情查询、余票查询都可能集中访问同一个 Key。我们主要做两层防护：第一层是 Caffeine 加载函数的原子合并，同一个 Key 同时 miss 时只会触发一次加载；第二层是在 Redis 回源阶段增加分布式锁和二次检查，获取锁后再次确认 Redis 是否已经被其他线程回填，没有数据才访问数据库，避免多个实例同时回源。

------

**Q：Caffeine 同 key 请求合并原理?多个线程同时 miss 为什么只有一次回源?**

A：我们使用的是 Caffeine 的原子加载能力，给缓存配置一个加载函数。同一个 Key 多个线程同时 miss 时，Caffeine 保证只有一个线程真正执行加载逻辑，其他线程等待加载结果，完成后共享同一个值返回。这样表面上是多个请求同时访问，实际只有一次真正的数据加载，这就是请求合并。

------

**Q：没有合并机制,击穿瞬间 MySQL 会被放大到多少倍压力?你能估算吗?**

A：放大倍数取决于缓存失效瞬间同时 miss 的请求数量。如果一个热点 Key 失效时有 N 个请求同时访问，没有任何保护，那么这 N 个请求都会直接访问数据库，数据库压力会被放大 N 倍。加入请求合并和双重检查后，大部分请求会等待第一次加载结果，真正访问数据库的请求数量会从并发数量降低到少量回源。

------

**Q：雪崩你们怎么防?本地缓存这层在雪崩时起什么作用?**

A：缓存雪崩主要是大量 Key 同时失效或者 Redis 故障，导致请求集中访问数据库。我们的防护主要是多级缓存和回源控制：Caffeine 和 Redis 两层缓存可以分散请求，热点数据即使 Redis 出问题，本地缓存仍然可以继续提供服务；同时读路径有请求合并和锁控制，限制数据库回源并发。另外缓存过期时间会做一定随机化，避免大量 Key 同时失效。本地缓存相当于数据库前的一层缓冲，可以在 Redis 异常或者缓存大面积失效时承接部分热点流量。

## 一致性

**Q：缓存更新为什么用"删除"而不是"更新"?业界共识的理由是什么?**

A：核心原因是避免并发写缓存导致旧数据覆盖新数据。两个请求同时更新同一份数据时，如果先提交的事务后写入缓存，旧值可能覆盖新值，导致缓存长期停留在错误状态。删除缓存不会有这个问题，数据库更新完成后删除缓存，下次查询自然回源加载最新数据。另外删除操作成本更低，不需要序列化完整对象，也避免了缓存层参与复杂业务逻辑。所以业界 Cache-Aside 模式通常采用"先更新数据库，再删除缓存"，让缓存只负责加速读取。

------

**Q：下单改了余票,缓存失效的时序?(先改库还是先失效)各有什么风险?**

A：我们分两类数据处理。节目详情这类基础数据采用"先更新数据库，再删除缓存并广播失效"的方式，这样删除前存在短暂读到旧数据的窗口，但最终会通过失效重新加载收敛。如果采用"先删缓存再更新数据库"，数据库更新失败时缓存会被重新回源填充旧数据，问题不大；真正风险是更新数据库成功后删除缓存失败，会导致缓存长期存在旧值，所以删除失败需要有补偿机制。余票这种高并发数据采用 Redis 作为实时库存源，Lua 脚本直接原子扣减 Redis，数据库作为异步投影，不存在传统缓存更新时序问题。

------

**Q：你们有没有机制保证 Redis 与 MySQL 最终一致?怎么对账?**

A：有，主要通过异步投影和定时对账保证最终一致。正常链路中，Redis 中的库存变化会通过投影任务同步到数据库；同时我们有定时对账任务，按照节目维度对比 Redis 中锁定、已售状态和数据库订单数据，发现 Redis 已扣减但数据库未落库，或者数据库存在订单但 Redis 状态不一致时，会记录异常并触发告警。对账的作用不是替代正常流程，而是作为最后一道防漂移机制，发现异常后推动数据修复。

------

**Q：缓存余票和 DB 不一致时,业务以谁为准?什么时候能收敛?**

A：抢票高峰期以 Redis 为准。因为余票扣减是在 Redis 中通过 Lua 保证原子性的，用户看到的库存以及下单校验都基于 Redis，数据库中的余票属于异步同步后的持久化数据。两者的不一致主要发生在 Redis 已经扣减但数据库还未完成投影的时间窗口，后续通过异步投影任务收敛，超时取消订单时也会同步回补库存。数据库主要承担持久化和对账作用，而不是实时库存来源。

------

**Q：热点节目一个 key 扛不住怎么办?你们怎么评估要不要处理?**

A：首先看热点是否真的成为瓶颈，主要评估两个方面：一个是读压力是否超过本地缓存和 Redis 的承载能力，另一个是写操作是否集中在单个 key 上串行执行。我们的余票已经按照节目和票档拆分 key，热点主要集中在少数热门票档；读请求通过 Caffeine 本地缓存和请求合并降低 Redis 压力，写请求通过 Redis Lua 保证单 key 原子扣减。如果未来单 key 确实成为瓶颈，可以继续细化拆分粒度，例如按座位维度拆库存，把热点压力分散到多个 key。目前压测结果还没有达到必须拆分的阶段。
