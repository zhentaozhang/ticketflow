# 主题三：Caffeine + Redis + MySQL 多级缓存 —— 面试深挖分析

> 基于"业务问题 → 技术方案 → 设计原因 → 实现方式 → 遇到问题 → 优化方案 → 极端情况处理"链路。
> 每个技术点按「是什么 / 为什么 / 怎么办」三层组织，代码锚点均经 codegraph 核实。

---

## 1. 项目背景

### 业务场景
抢票系统的读特性：**开票前大量用户反复刷新节目详情、票档、余票、座位**，这些是读多写少**的热点数据；而**开票瞬间的写（下单扣库存）又集中在少数热门节目上。读写都集中在热点，对缓存架构要求高。

### 原来的方案有什么问题
- **单层 Redis 缓存**：每次读取仍是一次网络 IO，QPS 上去后单靠 Redis 扛高频热点读会打满连接/带宽；热门节目**一个 key 被所有请求打**，Redis 侧也是热点；
- **无本地缓存**：同样的节目详情，每个请求都从 Redis 拉，重复网络开销；
- **数据变更后缓存不主动失效**：改了库，缓存还是旧值，存在脏读窗口。

### 为什么需要重新设计
需要**多级缓存**分摊压力：本地 Caffeine（进程内，零网络）→ Redis（共享、跨实例一致）→ MySQL（最终事实源）。同时要解决三件事：**多级之间的一致性**（本地缓存怎么被远程实例触发失效）、**缓存三大问题**（穿透/击穿/雪崩）、**余票数据的准确性**。

> 一句话背景叙述（面试开场用）：
> "节目详情、票档、余票这类热点数据读多写少，单层 Redis 扛不住高频访问且是单点热点。我们构建了 Caffeine + Redis + MySQL 三级缓存：本地缓存零网络开销扛高频读，Redis 做共享层，MySQL 是最终事实源。数据变更时通过 Redis Stream 广播失效事件，驱动集群所有实例的本地缓存主动失效，解决多实例本地缓存一致性问题；再配合布隆过滤器防穿透、Caffeine 同 Key 合并 + double-checked locking 防击穿、本地余票预判做售罄短路。"

---

## 2. 整体架构

### 三级缓存分层
```
Level 1  本地 Caffeine（进程内，零网络）
         └─ 节目详情/节目分组/场次/票档列表/节目分类
           过期策略：
             LocalCacheProgram         → 按"演出时间 - 当前时间"动态过期，演出结束自动失效
             LocalCacheTicketCategory  → 过期时长读 Redis 对应 key 的剩余 TTL，两级同生共死

Level 2  Redis（共享，跨实例一致）
         ├─ 节目/分组/场次/票档列表（普通 string 缓存）
         ├─ 余票 hash（PROGRAM_TICKET_REMAIN_NUMBER_HASH_RESOLUTION，HINCRBY 扣减）
         ├─ 座位三区 hash（未售/锁定/已售，下单时 field 流转）
         └─ 本地余票预判的数据源

Level 3  MySQL（最终事实源）
         └─ 程序库表：节目、票档、座位、场次
```

### 读链路（以节目详情为例，代码锚点 `getByIdMultipleCache` / `getById`）
```
查询节目详情
  → 前置守卫：布隆过滤器（ProgramBloomFilterCheckHandler.contains(programId)）
      不存在 → 直接 PROGRAM_NOT_EXIST（防穿透，不进入缓存）
  → Caffeine 本地缓存（localCacheProgram.getCache(key, function)）
      miss → getById：Redis →（double-checked locking）→ MySQL（createProgramVo）
  加载成功后逐级回填：DB → Redis → Caffeine
```

### 写/失效链路（本主题核心）
```
数据变更（下架/重置/下单扣库存）
  → 写 Redis / 写 MySQL（业务事务内）
  → redisStreamPushHandler.push(programId)  往 Redis Stream 写失效消息
  → 集群每个实例的 ProgramRedisStreamConsumer 消费到消息
  → programService.delLocalCache(programId)  本地 Caffeine 失效
  → 下次请求 miss → 从 Redis/DB 重建
```

### 本地余票预判（V5 特色，`ProgramLocalStockGate`）
```
进程内维护每票档的"预估余票"（ConcurrentHashMap）
  ├─ 惰性跟踪：只对"发生过下单"的票档生效，未跟踪返回 -1 不拦截
  ├─ 请求到达 Redis 前先 checkLocalStockGate()：预估不足 → 本地拒绝（售罄短路，零 Redis 消耗）
  ├─ Lua 扣减成功 → gate.deduct() 本地递减（用 Lua 返回的 remainMap 精确更新）
  └─ @Scheduled 每 2s 从 Redis 余票 hash 刷新校正漂移；空闲 30 分钟且余票为 0 的票档剔除
```

## 3. 核心技术方案拆解

---

### 技术点 A：为什么在 Redis 之上还要 Caffeine 本地缓存

**是什么**：节目详情、票档、分类等**读多写少**热点数据，除 Redis 外再加一层进程内 Caffeine 缓存。

**为什么**：
- **省网络 IO**：Caffeine 命中零网络往返（纳秒级），Redis 每次仍几十微秒到毫秒级；高频读场景下是数量级的提升；
- **给 Redis 减负**：10000 个并发请求读同一节目，若都打到 Redis 是 10000 次网络 IO；本地缓存命中后可能只有个位数请求真正落到 Redis；
- **扛本地读并发**：Caffeine 内部线程安全，同 key 并发 miss 自动合并。

**为什么不全用本地缓存**：
- 本地缓存**实例间不共享**：A 实例加载的数据，B 实例看不到；且每个实例都要自己预热，内存放大；
- 所以本地只放**最热、变化不频繁**的数据，共享和一致性交给 Redis。

**风险**：多实例本地缓存会存在**实例间不一致**（A 已失效、B 还有旧值）。
**优化**：这正是引入 Redis Stream 广播失效的原因。

---

### 技术点 B：缓存过期策略 —— 两级缓存"同生共死"

**是什么**：本地缓存的过期时间与 Redis 对齐，避免两级缓存"本地没过期、Redis 已过期"的错位。

**怎么做（代码锚点 `LocalCacheTicketCategory` / `LocalCacheProgram`）**：
- `LocalCacheTicketCategory`：`Expiry.expireAfterCreate` 直接读 `redisCache.getExpire(Redis key, MILLISECONDS)`，把 Redis 的剩余 TTL 作为本地缓存的过期时长；
- 更新/读取**不重置**过期时间（`expireAfterUpdate/expireAfterRead` 返回 currentDuration），保证两级同时到期，不给"本地旧值 + Redis 新值"留窗口；
- `LocalCacheProgram`：按"演出时间 - 当前时间"动态计算过期，演出结束后本地缓存自动失效，不用等到手动清。

**为什么这么做**：
- 本地 TTL 比 Redis 长：Redis 已刷新新值，本地还在提供旧值 → 读到过期数据；
- 本地 TTL 比 Redis 短：本地提前失效，白白增加对 Redis 的请求；
- 对齐后：本地缓存的生命周期严格 ≤ Redis，逻辑最简单、脏读窗口最小。

**风险**：依赖 Redis 的 TTL 值，Redis 不可用时读 TTL 会失败。
**优化**：读 TTL 失败时兜底用默认过期时长，缓存仍可用。

---

### 技术点 C：缓存穿透 —— 布隆过滤器挡在哪一层

**是什么**：**缓存穿透** = 查询一个**缓存和数据库都不存在**的数据。每次查询都 miss，直接打到 DB，恶意/低频请求可以借此压垮数据库。

**项目里的穿透风险点**：不存在的 programId 被反复查询（如扫描接口、脏数据）→ 每次 miss → 打 DB。

**为什么选布隆过滤器**（代码锚点 `BloomFilterHandler` + `ProgramBloomFilterCheckHandler`）：
- **原理**：位数组 + 多个哈希函数。元素写入时把对应位都置 1；查询时任一位置为 0 则一定不存在；
- **特点**：空间极小（几千万元素只要几 MB）、查询 O(1)，**能确定"一定不存在"**（零漏判），但存在"误判存在"（假阳性）；
- **挂在节目详情校验链上**：`ProgramBloomFilterCheckHandler`（executeTier=1 最早执行）里 `contains(programId)`，不存在直接抛 `PROGRAM_NOT_EXIST`，**在进入任何缓存/DB 之前就把无效查询挡掉**；
- 数据由 `ProgramBloomFilterInit` 启动时把所有上架节目 ID `add` 进过滤器。

**为什么不用"缓存空值"替代**：
- 空值缓存能挡，但恶意扫描会写入大量空值缓存，占用内存、污染缓存；真实数据出现后还要清空值缓存；
- 布隆过滤器用极小内存挡住绝大多数无效查询，干净利落。

**风险**：布隆过滤器**不能删除**（删除会破坏其他元素的位），误判存在无法纠正。
**优化**：项目里节目 ID 一旦生成不再删除，天然适配布隆过滤器；误判只导致个别无效请求放行，真实数据不受影响。

---

### 技术点 D：多级缓存一致性 —— 为什么用 Redis Stream 广播本地缓存失效（本主题最深点）

**是什么**：集群多实例下，本地 Caffeine 缓存是**各实例私有的**。A 实例发生数据变更后，要通知 B、C 实例把本地缓存也失效，否则它们还返回旧数据。本项目用 **Redis Stream 广播失效消息**实现。

**为什么选 Redis Stream（而不是 pub/sub）**：
- **pub/sub 的缺陷**：消息不持久化，消费者离线/断线期间的消息直接丢失；没有 ack 机制，消费失败无法重试；没有消费组，无法实现"组内竞争消费"；
- **Redis Stream 的优势**：消息追加式持久化在 Redis 中；有**消费组**（组内竞争、可回溯）；有 **pending/ack** 机制，消费失败消息不会丢；消费进度可控；
- 所以失效事件用 Stream，保证"变更了 → 各实例最终都能收到失效消息"。

**为什么用"失效"而不是"更新"本地缓存**：
- **失效简单可靠**：只删 key，不需要业务把新值完整算出来广播；
- **更新有竞态**：并发写本地缓存、值来源（哪个实例算的）不统一，反而复杂；
- Cache-Aside 语义下，失效 → 下次请求 miss → 从 Redis/DB 重建，天然正确。

**怎么做（代码锚点）**：
- 变更侧：`redisStreamPushHandler.push(programId)` 写消息（`RedisStreamPushHandler.push` 用 `StreamRecords.newRecord()` + `RecordId.autoGenerate()`）；
- 消费侧：`RedisStreamAutoConfig.streamMessageListenerContainer` 创建 `StreamMessageListenerContainer`，消费组模式下 `receiveAutoAck` 绑定消费者（`Consumer.from(group, consumerName)`）读 `StreamOffset.lastConsumed()`；
- `ProgramRedisStreamConsumer.accept()` 解析 programId → `programService.delLocalCache(programId)`；
- 消费线程池：`createThreadPool()` 核心=CPU 核数、最大=2×核数、队列 100、`CallerRunsPolicy` 拒绝策略（背压而非丢弃）、`batchSize=10`、`pollTimeout=5s`。

**风险**：Stream 消息消费失败/丢失，本地缓存就不失效 → 读到旧数据。
**优化**：本地缓存本身有 TTL 兜底（技术点 B），失效消息丢了最多延迟到 TTL 到期，最终一致；消费失败靠 ack/pending 机制可重放。

### 技术点 E：缓存击穿 —— 两层不同的防护（本主题深点之二）

**是什么**：**缓存击穿** = 一个**热点 key** 在缓存**过期/失效的瞬间**，大量并发请求同时 miss，全部打到 DB，DB 被瞬间压垮。

**项目里有两层防护，针对不同层**：

**第一层：Caffeine 同 Key 请求合并（本地缓存层）**
- Caffeine 的 `Cache.get(key, function)` 是**线程安全的原子加载**：同一时刻多个线程对**同一个 key** 调用 `get`，**只有一个线程真正执行 function 加载**，其余线程**等待并共享同一个结果**；
- 本地缓存失效瞬间，本实例内的并发 miss 会被合并成一次加载 → 不会放大。

**第二层：double-checked locking（Redis→DB 层，代码锚点 `ProgramService.getById`）**
- `getById` 标 `@ServiceLock(lockType = Read)`，先查 Redis；miss 后**手动获取 `ReentrantLock`，二次检查 Redis**（double check），仍未命中才查 DB 回填；
- 防止"多个线程同时发现 Redis miss、同时查 DB"的 cache stampede；
- 注释明确写了：`@ServiceLock(Read) 允许并发读，但防止 N 个线程同时进入该方法` + 手动锁二次检查，避免缓存过期瞬间重复加载。

**为什么需要两层**：本地层合并省进程内开销；Redis→DB 层因为 DB 才是重头，必须锁住防 stampede。两层配合，击穿瞬间 DB 只被压一次。

**风险**：本地缓存合并只对**单实例内**并发有效；跨实例靠每实例各自合并 + double-checked locking，DB 总压力 = 实例数，可控。
**优化**：配合本地余票预判（技术点 F）进一步挡掉售罄流量。

---

### 技术点 F：本地余票预判 —— 售罄短路（本项目特色）

**是什么**：`ProgramLocalStockGate` 在应用内存维护每票档的**预估余票**，请求到达 Redis **之前**先本地判断，售罄直接拒绝（不消耗 Redis 命令）。**注：这是代码里的"本地库存闸门"组件，面试表述用"本地余票预判"即可。**

**为什么需要**：
- 热门节目售罄后，**绝大多数请求都是来抢已售罄的票**；如果每个请求都打 Redis（Lua EVAL），Redis 被无效请求打爆；
- 本地先挡一道，售罄流量在进程内就被拒绝 → **零 Redis 消耗**，Redis 只服务"还有票"的请求。

**怎么做**（代码锚点 `ProgramLocalStockGate`）：
- **惰性跟踪**：只对"发生过下单"的票档生效，未跟踪返回 -1（不拦截），不污染冷数据；
- **请求前预判**：`checkLocalStockGate()` 用预估余票与请求数量比较，不足直接抛 `TICKET_REMAIN_NUMBER_NOT_SUFFICIENT`；
- **扣减后更新**：Lua 成功返回 `remainMap`（扣减后余票），`gate.track/deduct` 本地更新，无需额外 Redis 读取；
- **定时校正**：`@Scheduled(fixedDelay=2000)` 每 2s 从 Redis 余票 hash 刷新，纠正取消回补/库存重置的漂移；
- **内存保护**：空闲 30 分钟且余票为 0 的票档剔除，防止冷票档占内存。

**一致性说明（面试必讲）**：
- 预判是**加速器，不是权威**；正确性永远由 Redis Lua 原子扣减裁决；
- 与 Redis 短暂不一致（如取消回补），最多造成 ≤2s"假售罄"，由下次刷新纠正；
- 预判显示有票但实际无票 → 请求照常走 Lua，由 Lua 返回余票不足兜底。

**风险**：多实例各维护一份，实例间值不同（正常，因各实例扣减分布不同），靠定时刷新收敛。
**优化**：只挡"确定售罄"的请求，不确定的放行给 Lua 裁决——宁可多放也不误杀。

### 技术点 G：缓存雪崩 —— 如何防

**是什么**：**缓存雪崩** = 大量缓存 key **在同一时刻集体过期**（或缓存服务宕机），所有请求同时落到 DB，DB 被压垮。

**项目里的防护**：
- **本地缓存兜底**：即使 Redis 全部失效，本地 Caffeine 仍能扛住（读取不依赖 Redis）；
- **TTL 分散**：各业务 key 过期时长不同（节目按演出时间、票档对齐 Redis TTL），不会集中在同一时刻过期；
- **主动失效替代被动过期**：数据变更走 Redis Stream 失效，而不是等 TTL 自然过期，减少"到期瞬间的 miss 风暴"。

**风险**：Redis 整体宕机时，本地缓存命中率有限，重建路径（DB 加载）仍可用但会退化。
**优化**：本地缓存容量、多级回源 + 降级（DB 压力超限时短暂返回旧值）。

---

### 技术点 H：热点 Key —— 单 key 打爆的问题

**是什么**：热门节目详情/余票是**单个 key**，所有请求都打这一个 key；极端情况下单实例 Redis 单 key 的处理能力成为瓶颈。

**项目里的应对**：
- **本地缓存分担**：本地 Caffeine 把大部分热点读拦在进程内，Redis 上的单 key 请求量大幅下降；
- **本地余票预判**：售罄热点节目的写请求在本地短路，不打 Redis；
- 未做 key 拆分/读写分离（诚实说明边界）：当前量级下本地缓存已足够，若继续放大可再引入热点 key 拆分、多副本等手段。

---

### 技术点 I：缓存与数据库一致性 —— 删缓存 vs 更新缓存、失败兜底

**是什么**：数据变更时缓存怎么同步？本项目数据变更路径：**改 DB/Redis 操作 → 删 Redis 缓存 → Stream 广播删本地缓存**。

**为什么"删缓存"而不是"更新缓存"**：
- 更新缓存要**计算新值并写回**，且并发写缓存有竞态（A 算的旧值覆盖 B 的新值）；
- 删缓存成本低、语义简单：下次 miss 从 DB 读最新值重建，天然正确；
- 本项目写路径（下单扣库存）直接操作 Redis 余票 hash（HINCRBY），Redis 是操作权威，DB 通过异步投影/对账收敛（衔接异步下单主题）。

**失败兜底**：
- 删 Redis 失败：TTL 兜底，最终一致；重要数据靠定时刷新（预判每 2s 校正）；
- Stream 广播失败：本地 TTL 兜底 + Stream pending 可重放；
- 极端场景 `ProgramService.resetExecute`：重置 DB 后 `delRedisData`（Lua 批量删）+ `delLocalCache`，强制全量清理。

---

### 技术点 J：余票数据 —— 缓存为准还是 DB 为准

**是什么**：余票是**高频变化**数据，同时存在于 Redis（hash）、本地预判（内存）、DB（票档表 remain_number）。

**以谁为准**：
- **操作权威 = Redis**：下单时 Lua 直接 HINCRBY 扣减 Redis 余票，原子且高性能；
- **本地预判 = 加速器**：只拦"确定售罄"，不参与最终裁决；
- **DB = 最终事实源/对账基准**：座位状态、票档余量最终落 DB，靠投影任务 + 对账任务收敛。

**如何收敛**：
- 本地预判每 2s 从 Redis 刷新；
- DB 通过支付/取消回调 `operateProgramData` 更新余量（V5 下"未投影不扣、已投影归还"保证幂等）；
- 定时对账任务核对 Redis 扣减流水与 DB 落账（衔接异步下单主题）。

**风险**：Redis 与 DB 短暂不一致（扣了 Redis 未落 DB）依赖对账兜底。
**优化**：以 Redis 为操作权威保证并发正确，DB 异步收敛保证持久化正确。

## 4. 重点准备追问链（三层连问）

### 追问链 1：从"为什么用 Redis Stream"出发
- **第一层**：多实例本地缓存不一致怎么解决？
  - 答：数据变更时写 Redis Stream 广播失效消息，各实例消费后删本地缓存。
- **第二层**：为什么不用 Redis pub/sub？
  - 答：pub/sub 消息不持久化、无 ack、离线即丢；Stream 有持久化 + 消费组 + pending/ack，失效消息不丢。
- **第三层**：那失效消息万一丢了怎么办？
  - 答：本地缓存有 TTL 兜底（与 Redis 对齐），丢一条最多等到 TTL 到期，最终一致；Stream pending 机制可重放。

### 追问链 2：从"为什么本地缓存过期和 Redis 对齐"出发
- **第一层**：本地缓存过期时间怎么定？
  - 答：读 Redis 对应 key 的剩余 TTL，作为本地过期时长。
- **第二层**：为什么不对齐？
  - 答：本地比 Redis 长会读到过期数据；比 Redis 短会白多打 Redis。
- **第三层**：对齐了就能完全一致吗？
  - 答：不能完全一致，但配合 Stream 主动失效 + 过期兜底，实现最终一致。

### 追问链 3：从"缓存击穿怎么防"出发
- **第一层**：热点节目缓存失效瞬间会发生什么？
  - 答：大量并发 miss，全部打 DB，DB 被放大压垮（cache stampede）。
- **第二层**：你怎么防？
  - 答：两层——本地层 Caffeine 同 Key 请求合并（并发 get 只有一次加载）；Redis→DB 层 double-checked locking（锁 + 二次检查后再查 DB）。
- **第三层**：跨实例呢？
  - 答：每实例各合并/锁一次，DB 总压力 = 实例数，可控；再配合本地余票预判挡售罄流量。

### 追问链 4：从"本地余票预判"出发
- **第一层**：预判会不会导致误拒绝？
  - 答：显示无票才拒绝；且只拦"确定售罄"，不确定的放行给 Lua 裁决。
- **第二层**：预判怎么保证和 Redis 一致？
  - 答：Lua 成功返回 remainMap 精确更新 + 每 2s 定时从 Redis 刷新校正。
- **第三层**：预判是权威吗？
  - 答：不是，只是加速器；正确性永远由 Redis Lua 原子扣减裁决，预判错误最多造成 ≤2s 假售罄。
