# 优惠券秒杀模块 — 实现思路与工作留痕

> 本文按个人开发者的真实开发过程记录：先想清楚什么、踩了哪些坑、怎么排查解决的、最终怎么验证的。
> 环境：macOS (Apple Silicon) / JDK 23 / Maven 3.9 / 本机 MySQL 9.6 + Redis 7 / 无 Docker / 无 Kafka
> 分支：`feature/coupon-seckill`

---

## 0. 起因与目标

公司主项目是 `ticketflow`（Spring Boot 3.3 + Spring Cloud Alibaba 的微服务票务系统，下单链路已经做过 V5 优化：Redis Lua 原子收敛 + Kafka 异步落库）。现在要加"优惠券秒杀"：活动期间高并发抢券，抢到后购票立减。

我的判断是：**先别急着往现有微服务里塞**。秒杀的流量模型（瞬时高并发、读多写少、结果异步）和普通交易差异很大，直接集成会互相干扰。所以先在独立分支上做一个**单体验证应用**，把完整业务流程、并发方案、一致性问题全部跑通，确认可行了再以独立服务的形式并回去。这也是和负责人对齐过的路线。

前置调研结论（对着现有代码看的，不是拍脑袋）：
- 现有 `order-service` 已经用 Kafka topic `create_order`、48 并发消费、Lua 脚本外置预加载 —— 我的秒杀模块要**刻意对齐这套风格**，集成时才不违和。
- 现有分库分表是 `order_0/order_1` 这种按 `user_id` 分片的模式 —— 秒杀的用户券表也应该照这个思路。
- 全仓库没有优惠券相关代码 —— 全新模块，没有兼容包袱。

## 1. 环境准备（一上来就踩坑）

### 1.1 本机 Java 是 23，项目目标 Java 17
`java -version` 显示 Corretto 23，但设计文档定的 Java 17。解决办法：pom 里用 `maven.compiler.release=17`，JDK 23 编译 17 目标没问题。**第一个坑**：Spring Boot 3.3 的 parent 不自动带 Lombok 的 annotationProcessorPaths，JDK 23 下 classpath 上的 Lombok 注解处理器**不会被自动发现**，所有 `@Data` 的 getter/setter 全编译不过，报一屏"找不到符号 getXxx()"。解决：在 maven-compiler-plugin 里显式声明：

```xml
<annotationProcessorPaths>
  <path>
    <groupId>org.projectlombok</groupId>
    <artifactId>lombok</artifactId>
    <version>1.18.38</version>
  </path>
</annotationProcessorPaths>
```

### 1.2 MySQL 装了但没启动，root 密码还忘了
`brew services list` 看到 mysql 是 `none`（没启动），`mysql -uroot` 直接 Access denied。折腾了几个方案后，用最直接的：停服务 → `mysqld_safe --skip-grant-tables` 起 → 登录后 `ALTER USER 'root'@'localhost' IDENTIFIED BY ''` → 正常重启。之后建库 `coupon_seckill`。

### 1.3 Docker 不可用 → 测试基础设施的思路被迫调整
本来想用 Testcontainers 起 MySQL/Kafka 做集成测试，结果 Docker daemon 没跑。替代方案：
- 集成测试用**本机真实 MySQL + 真实 Redis**（都起得来），测试库单独建 `coupon_seckill_test`。
- 一开始还引入了 `wix-embedded-mysql`（纯 Java 嵌入式 MySQL）想兜底，结果它的传递依赖 `jna-4.0.0.jar` 在本地 Maven 仓库是坏的（Invalid CEN header），直接移除这个依赖，统一用本机 MySQL。
- Kafka 没装也没法装（无 Docker）—— 这里做了个关键设计（见 §3.2）。

## 2. M1：单体骨架 + 活动管理

### 2.1 独立 pom，不继承根 pom
这是刻意的：根 pom 是微服务多模块的 parent，直接加模块会污染整个构建（比如 `ticketflow-common` 等框架模块都得跟着编）。独立 pom 只是**版本对齐**（Spring Boot 3.3.0、MyBatis-Plus 3.5.7、Lombok 1.18.38），依赖自己声明。等集成阶段再把这些依赖替换成 `ticketflow-*` 框架模块。

### 2.2 建表脚本：6 张表，其中 2 组分表
`sql/schema.sql`：
- `coupon_template`（券模板）、`flash_sale_activity`（秒杀活动，库存内嵌）—— 单表
- `flash_sale_order_0/1`、`user_coupon_0/1` —— 按 `user_id % 2` 分表

设计取舍：
- **库存直接放在活动表里**，不单独拆 inventory 表。理由：一个活动就一个 SKU（一张券），单行库存 + 乐观锁 `version` 就够了，避免多行库存的一致性噩梦。后续要支持多 SKU 再拆。
- 分表**不做数据搬移**（库表结构从第一天就按分片建），用 MyBatis-Plus 的 `DynamicTableNameInnerInterceptor` + 一个 `ShardingContext`（ThreadLocal 存 userId）在运行时把逻辑表名 `flash_sale_order` 换成 `flash_sale_order_{userId%2}`。这跟现有 `order_0/1` 的规则一致，集成时把拦截器换成 ShardingSphere 即可。

分表有个必须注意的点：**ThreadLocal 一定要在 finally 里 clear**，不然线程池复用线程会串号，用户 A 的数据写进用户 B 的分片。我专门写了个 `ShardingContextTest` 验证了线程隔离。

### 2.3 活动管理：乐观锁 + Redis 预热
管理端四件事：创建模板、创建活动（草稿）、发布、下架/调库存。
- 发布时 `草稿 → 未开始` 用乐观锁（`version` 条件更新），并发下只有一个人能发布成功。
- 发布同时**预热 Redis**：`flash:meta:{id}`（JSON：startTs/endTs/limit）+ `flash:stock:{id}`（总库存）。预热是秒杀的第一步，meta 供抢购脚本做权威校验。
- 校验规则里有个细节：创建活动时 `endTime` 加了 `@Future` 注解 —— 所以**管理端根本建不出"已结束"的活动**（业务上合理），但这也让我后面想测"已结束抢购"时多花了一步（见 §5.4）。

## 3. M2：抢购主链路（核心中的核心）

### 3.1 为什么同步路径只做 Redis，而且是一个 Lua 脚本
秒杀峰值 QPS 会到几万，如果同步去写 DB（行锁、连接池、网络往返），DB 先跪。所以设计是：

```
请求 → 网关校验/限流 → 本地缓存快速失败(活动状态) → Redis Lua 原子扣减 → 返回"排队中"
                                                                    ↓
                                     Kafka 异步：落库(流水+用户券) → 回写结果
```

**扣库存、限购计数、请求幂等、时间窗校验，全放一个 Lua 脚本里原子完成**（`grab.lua`）。为什么不用 `DECR` + 应用层判断？因为多步操作非原子，并发下会超卖；为什么不用分布式锁？锁的获取释放开销大，而且锁粒度不好控，Lua 脚本是 Redis 官方推荐的原子方案。这跟现有 V5 项目的取向一致（"能 Lua 就不加锁"）。

脚本要点（写的时候反复推敲过的）：
- 时间窗校验在**脚本内**做，不在应用层做 —— 否则"应用层校验通过、请求到达 Redis 时活动刚好结束"的竞态会漏放。
- 库存 `DECR` 到负数立即 `INCR` 回加 —— 库存**永不出现负值**。
- 限购计数用 `INCR` + 按活动剩余时间设 TTL，活动结束自动清理。
- 幂等标记 `SET NX EX`（dedup key），**失败场景会删掉标记**（这样用户换 requestId 或重试时不会被误伤），成功场景保留 60 秒。

### 3.2 Kafka 缺席怎么办：消息抽象 + mock 实现
没有 Kafka，但架构上必须保留 Kafka 削峰的位置。做法：定义 `FlashSaleMessagePublisher` 接口，两个实现：
- `KafkaFlashSaleMessagePublisher`（生产）：`kafkaTemplate.send(topic, userId, json)`，key=userId 保证同用户有序，`acks=all` + 幂等 producer。
- `MockFlashSaleMessagePublisher`（本地/测试，`mock-messaging=true`）：线程池 + 直接调用消费逻辑，模拟"异步投递 + 削峰"。

用一个 `@ConditionalOnProperty` 切换。这样：
- 没有 Kafka 也能把"抢购 → 异步发券 → 结果查询"全链路跑通（本地验证、CI 都能跑）；
- 消费逻辑**只有一份**（`FlashSaleIssueHandler`），Kafka 模式和 mock 模式共用，不会出现两套逻辑漂移。

### 3.3 发券落库的幂等：唯一索引是最后一道闸
异步消费最怕重复投递。三层防御：
1. 抢购时 Lua 的 dedup 标记（第一道，挡住绝大多数重复请求）；
2. 落库前查 `(activity_id, user_id, request_id)` 唯一索引，已存在直接返回；
3. **并发下两个线程同时查到不存在** → 都 insert → 唯一索引冲突 `DuplicateKeyException` → catch 住视为已处理。

消息体里带 `order_no`（雪花 ID 生成），`uk_order_no` 也是唯一索引 —— 消息级的最后一层兜底。

### 3.4 发送失败立即回补，不悬挂库存
"Lua 扣了库存，但 Kafka 消息没发出去"是必须处理的不一致窗口。做法：publish 抛异常 → 立即执行 `rollback.lua`（库存 INCR、限购 DECR、删幂等标记）→ 返回"系统繁忙"。

但这里有个**诚实的技术判断**：如果 Kafka send 是"超时"（消息可能实际已发出），立刻回补存在极小概率和消费端重复发券叠加导致多回补。所以生产上这个窗口**最终由对账任务收敛**（见 §4.3），回补只是把窗口缩到最短。我在代码注释里写明了这个边界，不装完美。

### 3.5 一个隐蔽的注入坑：@Qualifier 不随 Lombok 构造器走
`FlashSaleGrabService` 依赖两个 `DefaultRedisScript<Long>`（grab 和 rollback），必须用 `@Qualifier` 区分。我一开始写在字段上配合 `@RequiredArgsConstructor` —— 启动直接报 `NoUniqueBeanDefinitionException`。原因：**Lombok 生成的构造器不会把字段上的 `@Qualifier` 复制到构造参数上**。排查后改成字段注入（`@Autowired @Qualifier` 直接放字段），三个用到脚本的类统一这么处理。

## 4. M3：用券闭环 + 对账

### 4.1 锁券为什么是"Redis 第一道闸 + DB 乐观锁"
购票下单要防止同一张券被两个订单同时用。方案：
1. Redis `SETNX coupon:lock:{couponNo}`（值=订单号，带 30 分钟 TTL 防死锁）—— 挡住绝大多数并发；
2. DB 乐观锁 `UPDATE ... SET status=已锁定 WHERE status=未使用` —— Redis 只是"第一道闸"，**DB 状态才是最终事实**，Redis 挂了也不至于双花；
3. 乐观锁没命中（券已用/已锁）时，要释放"仍属于本订单"的 Redis 锁，避免留下脏锁。

这里和抢购不同：**用券环节要强一致**（涉及订单金额，不能"最终一致"），所以走 DB 事务 + 乐观锁，Redis 只做性能闸门。

### 4.2 状态机
- 活动：草稿 → 未开始 → 进行中 → 已结束；进行中可紧急下架。由 `ActivityStateTask` 定时推进 DB 状态（抢购的权威校验始终在 Lua 的时间窗，不依赖这个任务）。
- 用户券：未使用 → 已锁定 → 已使用（支付成功）；已锁定 → 未使用（订单取消退回）；过期批量置灰。

### 4.3 对账任务：最终一致性的收敛器
Redis 和 DB 长期不一致是必须防的。`ReconcileTask` 每 60 秒跑一遍：
- **库存对账**：对每个进行中的活动，校验 `Redis 剩余库存 + DB 已发券数 == 总库存`，不一致**以 DB 为权威重载 Redis 库存** + 告警日志。测试里我故意把 Redis 库存改成 999，跑一次对账就修正回正确值。
- **限购对账**：按分片扫 `GROUP BY user_id HAVING COUNT > limit` 的超发用户，告警（修复动作留给运营确认）。
- 另有 `IssueTimeoutTask`（处理中流水超 5 分钟 → 标记失败 + 回补库存）、`CouponExpireTask`（过期券批量置灰）、`DltConsumer`（Kafka 死信回补，生产模式装配）。

对账 SQL 是**跨分片**的，这里有个实现细节：分表拦截器只处理逻辑表名，对账 SQL 显式传物理表名（`${table}` 来自 `ShardingContext.shardTable`，值由内部常量生成，没有注入风险），遍历 `_0`/`_1` 求和。

## 5. 测试：先写测试，把问题都暴露出来（本轮重点）

### 5.1 测试分三层
| 层级 | 依赖 | 类 | 数量 |
|------|------|----|----|
| 纯单元（Mockito） | 无 | `SnowflakeIdGeneratorTest` / `ShardingContextTest` / `ManageServiceTest` / `FlashSaleGrabServiceTest` / `CouponIssueServiceTest` / `CouponUseServiceTest` | 35 |
| 脚本级 | 本机 Redis（无则跳过） | `GrabLuaScriptTest` | 7 |
| 集成 | 真实 Redis + MySQL | `FlashSaleGrabIT` / `CouponUseIT` | 11 |

集成测试用真实中间件（本机就有），重点验证：**100 并发抢 50 库存恰好 50 成功零超卖、同 requestId 20 线程并发只放行一次、20 并发锁同一券只有一个订单赢、对账修正被篡改的 Redis 库存**。

### 5.2 纯单元测试踩的坑（记录一下，都是真实花时间排查的）

**坑 1：Mockito 纯单测里 MyBatis-Plus 的 LambdaWrapper 直接炸**
`new LambdaUpdateWrapper<UserCoupon>().set(UserCoupon::getStatus, ...)` 在纯单测环境抛 `MybatisPlusException: can not find lambda cache for this entity`。原因：lambda 解析依赖 `TableInfo`，正常由 Mapper 加载时初始化，而 Mockito 测试根本没加载 Mapper。解决：写了个 `MpTableInit` 工具，`@BeforeAll` 里手动 `TableInfoHelper.initTableInfo` 初始化 4 个实体的列缓存。

**坑 2：Mockito 的 varargs stub 不命中，还分"单元素模式"和"数组模式"**
`StringRedisTemplate.execute(RedisScript, List, Object... args)` 是 varargs 方法，stub 它的时候：
- 用 `any()` 或 `any(Object[].class)` 都**不命中**（`any()` 是"恰好一个 vararg"语义，调用传了 2 个参数就不匹配）；
- 混合原始值和匹配器直接 `InvalidUseOfMatchersException`（Mockito 要求全匹配器或全原始值）；
- 最后用 `eq(grabScript), anyList(), anyString(), anyString()`（每个 vararg 一个匹配器）才稳定命中。
这个坑用临时"探针测试"逐步隔离定位的（打印每一步结果），定位完删除探针。

**坑 3：@InjectMocks 不注入带 @Autowired 的字段**
`FlashSaleGrabService` 的 `grabScript`/`rollbackScript` 是 `@Autowired` 字段注入（因为坑 4 的 @Qualifier 问题），`@InjectMocks` 只做了构造器注入，这两个字段是 null，导致 stub 全部落空、请求全走"系统繁忙"。解决：不用 @InjectMocks 的魔法，`@BeforeEach` 里**手动 new 服务 + `ReflectionTestUtils.setField` 注入脚本 mock**，可控、可读。

**坑 4：Mockito 严格模式报 UnnecessaryStubbing**
`setUp` 里统一 stub 了 `opsForValue()`，但部分用例根本不用 → 严格模式直接报错。解决：用 `lenient()` 标记或只在需要的用例里 stub。

**坑 5：surefire 默认不跑 *IT 类**
`mvn test` 只跑 `*Test`，集成测试（`*IT`）不执行，差点误以为全绿。在 pom 的 surefire 配置里显式 include `**/*IT.java`，`mvn clean test` 一次跑全 53 个。

### 5.3 Lua 脚本测试：直连本地 Redis，不启动 Spring
`GrabLuaScriptTest` 手动建 `LettuceConnectionFactory` + `StringRedisTemplate`，直接执行 `grab.lua`/`rollback.lua`，覆盖：正常扣减、库存耗尽（含**负库存回加**断言）、限购、同 requestId 幂等、meta 缺失、时间窗外、回补恢复。用 `Assumptions.assumeTrue` 探测 Redis，连不上自动跳过，不污染 CI。

### 5.4 测"已结束活动"时的一个小插曲
想验证抢"已结束"的活动返回 50011，结果发现**管理端根本建不出过去时间的活动**（`@Future` 校验，业务上合理）。于是直接改 DB 的 `start_time/end_time` 为过去、手动重写 Redis meta 模拟"活动已结束"，才把 `-3 → mapNotActive → 50011` 这条兜底路径测到。这也验证了兜底逻辑确实存在（Lua 返回 -3 后查 DB 区分具体原因）。

## 7. 沉淀下来的几条原则

1. **秒杀同步路径只碰 Redis，DB 永远异步化**——这是容量和一致性的分水岭。
2. **能 Lua 原子解决就不上分布式锁**——锁是最后手段，且要控制粒度。
3. **幂等靠"唯一索引兜底"，不靠"先查后插"**——并发下查了也没用。
4. **Redis 是并发权威，DB 是最终事实**——不一致由对账任务以 DB 为准收敛，并告警。
5. **测试分层**：纯单元（快、无外部依赖）→ 脚本级（直连中间件）→ 集成（真实环境），每层职责不同，一层坏了不影响另一层定位。
6. **踩过的坑写下来**：Lombok×@Qualifier、Mockito×varargs、@InjectMocks 注入边界、surefire×IT——这些不记下来，下次还要再花一遍时间。
